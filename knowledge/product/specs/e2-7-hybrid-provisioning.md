# Spec: E2.7 Hybrid via Graph (checkpoint 2c slice)

> An admin connects an Entra tenant with a certificate-authenticated app that holds a closed, named permission set and then creates a hybrid user in **one** flow: one preview that shows the AD half and the cloud half, one approval, and a status that says plainly what is done, what is waiting for Microsoft's sync and why. The default path needs no profile-write permission in Entra. The cloud half never touches an object activeDIQ cannot prove it created.

Planned off-board on the second machine (CEO decision 2026-11-10, `knowledge/memory/decisions-log.md`): documents only, no product code, no ticket IDs. Attach board IDs at merge. **No Entra tenant exists yet** (action A-0026, deferred until M1 acceptance), so every Microsoft behaviour below is sourced inline or tagged `[UNVERIFIED]` (needs the Entra sandbox, D-0001) or `[DISCOVERY]` (needs a pilot). Round 3 (2026-11-11) closes the round-2 findings (list at the end). The round 1→2 responses moved to the [security review](reviews/2026-11-11-m2c-security-review.md) (`### E2.7 round 1→2 responses`). Entra inventory sync (FR-36…38) is split out to [e2-7a](e2-7a-entra-inventory-sync.md).

Binding sources: [ADR-0005](../../development/decisions/0005-operation-pipeline-and-audit-trail.md) **plus the amendment of §14.1** (not buildable on ADR-0005 alone), [ADR-0002](../../development/decisions/0002-deployment-model.md) rules 3, 7, 8, 9, [domain model](../../development/domain/domain-model.md) DM-10, 16, 20, 21, 35, 40…42, 50, 70, [threat model](../../development/architecture/threat-model.md) §6.6, §6.8–6.9, TM-D1, D2, D17, D19, D23, D25, [safe-primitives-odata](../../development/architecture/safe-primitives-odata.md) (P8), [connector contract](../../development/architecture/connector-contract.md) §6.6, §8, [forest connection spec](ad-forest-connection.md) (its §14 hands the Entra connection and attestation to this spec), [M2 plan](../../business/scoping/m2-plan.md).

## 1. Problem and user

Hybrid is the normal case for the migrating customer: "Most ADMP customers run hybrid" ([ADMP research §7a](../../business/market-research/manageengine-admanager-plus.md)). In ADManager Plus the cloud half lives in a separate app: the M365 tab is an embedded Ember app with its own navigation, and the research records a ~26 s render and ~64 action links in the demo ([ADMP research §4.1–4.2, W8](../../business/market-research/manageengine-admanager-plus.md); single-session, indicative). Reviewers say "cloud requires another product" (~11 reviews, X5, [customer voice](../../business/market-research/manageengine-ad-customer-voice-and-security.md)). ADMP's orchestration cloud actions "work only on users synced by DirSync" (ADM-169, W15), and the research does not say what happens before the user has synced `[UNVERIFIED]`.

- **AD admin / help-desk technician** creates joiners daily to weekly. *When a new hire starts, I want the AD account, the M365 licence and the right groups created from one form, so I can hand over a working identity without opening a second tool.* Source: ADM-027 baseline.
- **AD admin (once per tenant)** connects the tenant (ADM-159, I360-003). *When I connect Microsoft 365, I want to know the app can do licences and groups and nothing else, so I can approve it with the security team.* Source: ADR-0002 rules 7–9; TM-D1.
- **Security / SOC analyst.** *When a hybrid user is provisioned, I want proof the cloud half touched only the object we created.* Source: TM-D17 (takeover through hard/soft match).
- **IT manager / auditor.** One audit record across AD and Entra. **End user:** no interaction in 2c.

What it costs today in ManageEngine: a second surface, a separate M365 service account for bulk MFA and Teams policy ([ADMP research §2.3](../../business/market-research/manageengine-admanager-plus.md)), and no documented handling of the sync gap `[UNVERIFIED]`.

**The technical fact that shapes the spec.** An AD user created by activeDIQ does not exist in Entra until the customer's sync client copies it. Entra Connect Sync runs a cycle every 30 minutes by default; a delta cycle is started with `Start-ADSyncSyncCycle -PolicyType Delta` on the sync server ([scheduler](https://learn.microsoft.com/en-us/entra/identity/hybrid/connect/how-to-connect-sync-feature-scheduler)). Cloud Sync is described as every two minutes, but Microsoft's pages disagree (the FAQ says roughly 10 to 20 minutes for user provisioning) ([what is Cloud Sync](https://learn.microsoft.com/en-us/entra/identity/hybrid/cloud-sync/what-is-cloud-sync), [how it works](https://learn.microsoft.com/en-us/entra/identity/hybrid/cloud-sync/concept-how-it-works), [FAQ](https://learn.microsoft.com/en-us/entra/identity/hybrid/cloud-sync/reference-cloud-sync-faq)). The licence and the cloud groups can only be applied after that copy exists **and** activeDIQ has proved it is the same identity (DM-20.I4).

**Cloud-only users:** not created in 2c. The Actions, the `entra_tenant` scope and the Plan/verify path are the same, so slice 2c-b adds them without a new architecture.

**Scope impact of round 2.** Licensing a user by membership of a licensed cloud group is the **default** (FR-26): it needs `GroupMember.ReadWrite.All` and neither `LicenseAssignment.ReadWrite.All` nor `User.ReadUpdate.All`. What stays in 2c-b is assigning a licence *to a group*. The demo promise is met on the default path. Wizard preconditions: the tenant has a licensed cloud group, and the hire's location equals the tenant location, because a user with no usage location inherits the tenant's location under group-based licensing ([group licences](https://learn.microsoft.com/en-us/microsoft-365/admin/manage/manage-group-licenses?view=o365-worldwide); for multi-location tenants Microsoft advises setting the location at creation, hence the opt-in family). Entra delta sync and the datasets (FR-36…38) are the separate build slice [e2-7a](e2-7a-entra-inventory-sync.md); no new parity ID.

### Unhappy paths
No permission, family off, tenant not attested, group `tier0`, group not on the writable list, no available units, missing usage location on the direct path: the request is refused at **Plan** with the reason, the field and the fix, and **no AD write happens** (FR-10); each offers "continue without the cloud steps". After the AD write: tenant attestation lapses, correlation not `matched`, authority lost, throttled, Graph unreachable, expiry (FR-16…21) leave the AD user in place, show the per-step list, and offer **Undo**. Sync late: "late" banner with causes. 10k results: pickers are searchable and paged. Empty states: no tenants, no licensed groups or SKUs, no hybrid link.

### 7.1 Tenant connection (ADM-159, I360-003)

| ID | Requirement | Parity / enh |
| --- | --- | --- |
| FR-01 | The system MUST connect one Entra tenant per Entra connection (DM-10 `entra_tenant`) using the customer's own app registration with certificate credentials generated by activeDIQ; the private key MUST stay sealed under the tenant key and MUST NOT be shown or returned; the console and API MUST NOT accept a client secret (ADR-0002 rules 3, 8). | ADM-159, I360-003, E4 |
| FR-02 | Several tenants MAY be connected (many-to-many domain-tenant links via DM-21), each with its own credential and binding. | ADM-159 |
| FR-03 | Verification MUST run EV1 (token), EV2 (tenant identity = `directory_identity`, fixed at first verification, DM-10.I1), EV3 (over-privilege), EV4 (read and enabled-write sufficiency), EV5 (excess, warn only) (connector contract §8.4, DM-24). EV3 MUST fail on any TM §6.6 deny-list permission, any directory role (active or eligible) and any unexpired password credential. **For an Entra connection in 2c an EV3 failure MUST NOT be acknowledgeable** (DM-24 allows a DM-25 acknowledgement; the stricter rule is a DM-24 follow-up, §14.3). A rotation's pending certificate is not an "extra key" (FR-39). | ADM-159, E4 |
| FR-04 | The 2c application-permission set is closed and grouped in **families**. **Read (always):** `User.Read.All` ([user delta](https://learn.microsoft.com/en-us/graph/api/user-delta?view=graph-rest-1.0)), `GroupMember.Read.All` (group delta, TM §6.6), SKU reads via `LicenseAssignment.Read.All` ([subscribedSkus](https://learn.microsoft.com/en-us/graph/api/subscribedsku-list?view=graph-rest-1.0): least privileged), and the tier-0 guard reads `Directory.Read.All`, `RoleManagement.Read.Directory` and the two PIM-for-Groups reads. **Group membership (on by default):** `GroupMember.ReadWrite.All` ([add members](https://learn.microsoft.com/en-us/graph/api/group-post-members?view=graph-rest-1.0): least privileged for a user member); it carries the licensed-group path (FR-26); it is tenant-wide membership write, bounded by FR-41, and its wizard and EV5 text MUST say so. **Licences, direct (opt-in):** `LicenseAssignment.ReadWrite.All` ([assignLicense](https://learn.microsoft.com/en-us/graph/api/user-assignlicense?view=graph-rest-1.0)). **Usage location (opt-in, off by default):** `User.ReadUpdate.All` ([update user](https://learn.microsoft.com/en-us/graph/api/user-update?view=graph-rest-1.0): least privileged for `PATCH /users/{id}`; `usageLocation` is not among the page's listed exceptions, so the documentation covers it, confirm in lab G3). Its EV5 text MUST say the grant is tenant-wide profile write and that Microsoft documents no property-specific permission for `onPremisesImmutableId` or `userPrincipalName` (confirm in lab G3 extended, OQ-F4). **Change monitoring (recommended whenever a HybridLink exists, FR-06):** `AuditLog.Read.All`. **`Policy.Read.ConditionalAccess` is required whenever the Group-membership family is on** (TM-D25 rule 9, FR-41). The system MUST NOT request `User.ReadWrite.All`, `Directory.ReadWrite.All`, `User.Create`, `Group.ReadWrite.All` or `Synchronization.ReadWrite.All` (deny list). EV5 MUST NOT flag `AuditLog.Read.All` as excess while a HybridLink exists. A permission an *enabled* family needs and the app lacks MUST disable that family with the permission named (EV4 warn for writes, block for reads). | ADM-159, E4 |
| FR-05 | Every Graph call MUST be application-only. Delegated Graph calls are limited to the one attestation read (FR-06). Rationale: delegated licence and group writes would run as the signed-in admin and need Entra roles ([assignLicense roles](https://learn.microsoft.com/en-us/graph/api/user-assignlicense?view=graph-rest-1.0): License Administrator, User Administrator…), which ADR-0002 rule 7 keeps out of the product. | E4 |

**Activation digest rules (security ruling R2-A.2: the two-stage binding is accepted on these six conditions).** `objectGUID` does not exist at Plan, so the approver's signature commits to a *rule*, and the digest fixes its one free input:
- **D1 · The plan hash commits to the derivation.** It names the operation, item and step whose result supplies `objectGUID`; the anchor rule (`anchor_attr`, base64 of `objectGUID`); the tenant connection and its `directory_identity`; and the approval-window constant (24 h). Every digest input is then in the plan hash or is the create step's recorded result.
- **D2 · One writer, one moment.** The continuation writes `objectGUID`, anchor, `approval_valid_until` and `activation_digest` exactly once per continuation row, in the same transaction that records the AD item `succeeded`, from the create step's own result (FR-14). No verify retry or re-plan writes them. A Resume writes them only into its own new row (D3).
- **D3 · Write-once in storage.** These HybridRequest columns have no UPDATE path for the runtime role (a guard trigger, as on `authn_accounts`). **A Resume always copies `objectGUID` and the anchor** and never re-reads or recomputes them. It copies `approval_valid_until` and the digest **only on carry-over** (FR-18, after `cloud_step_failed`). After a new approval, the new continuation row writes its own `approval_valid_until` and digest once, by D2…D6 relative to the new approval (the D1 supplying step is still the original's create step), with its own `objects.hybrid.awaiting_sync.started` (D4). That is a new write-once row, never an UPDATE (A3-m1 = H3-m1).
- **D4 · In the audit chain at birth.** `objects.hybrid.awaiting_sync.started` is written in the D2 transaction and carries `plan_hash`, `objectGUID`, anchor, tenant ID, `approval_valid_until` and the digest, chained at commit (DM-80.I1), so an auditor recomputes the digest from one event.
- **D5 · Recompute, don't trust.** Before every cloud write the executor recomputes SHA-256(plan hash ‖ `objectGUID` ‖ anchor ‖ tenant ID ‖ `approval_valid_until`) from the D3 values, in a fixed-width canonical encoding (never string concatenation), and compares it with the digest the step token binds; a mismatch refuses the token.
- **D6 · Absolute cap.** `approval_valid_until` ≤ approval time + `plan_valid_until` (1 h) + AD verify window + 24 h, asserted at D2. For a Resume with a new approval, "approval time" is that new approval's time.

## 8. Pipeline fit (ADR-0005)

What this spec uses **unchanged**: Plan is read-only; `plan_hash` over steps, diffs, reversibility and secret-input flags (rule 9); one approval (rule 8, SoD, step-up for Irreversible); a step token per claimed step (rule 2); read-then-write idempotency and `already_applied` (rule 4); the `tier0` guard and `tier0_after_write` (rule 7); verify windows and 429 handling (four concurrent writes per tenant); undo as a new Operation in reverse order, planned against live state.

What it **cannot** do on ADR-0005 as ratified, which the amendment of §14.1 supplies: a wait or gate step (rule 3 has no wait and no `running → planning` edge); items that block as a group (rule 1); an outcome for "AD done, cloud refused" inside the closed result sets (rule 3); a Resume that supersedes a live continuation; a target that does not exist at Plan (rules 1, 7, 9); and `plan_valid_until` (1 h) being shorter than a sync cycle.

**Ownership (H2-M1).** `objects` owns the HybridRequest / continuation entity, the gate-condition evaluator and the `objects.hybrid.*` audit kinds (blueprint: ADM-027 is `objects`; the `m365` module owns the licence Actions beside it). The condition ("the Entra object exists, is `matched` and is the right one") is **declared on the Action descriptor** by its owner (`Descriptor.Waits`: a named `WaitCondition` whose evaluator the module supplies through `Registrar.Action`; no new extension point; ADR-0005 already uses `Gate` for the rule 8 approval gate, so the seam and the step kind `wait` avoid that name, H3-n1). The evaluator reads correlation only through `inventory`'s read API. `platform/operation` holds only the generic gate state machine and the sweeper deadline, evaluates only the declared condition, and imports no module or directory package (ADR-0005 rule 13, ADR-0003).

## 9. Data and API impact

- **Graph resources:** `users/{id}` (read; `assignLicense`; PATCH `usageLocation`), `users/delta`, `groups/delta`, `subscribedSkus` (read), `groups/{id}` and `members/$ref`, `users/{id}/licenseAssignmentStates` (read), `organization` (verified domains, tenant location; read), `identity/conditionalAccess/policies` (read, FR-41). All URLs through the P8 builders (`graph.Client.Unique`, `Key(GUID)`); no `$filter`/`$search` literal outside the home package; `@odata.nextLink` followed only after the host pin (P8 V12).
- **Actions:** group membership = Entra arm of the existing `objects` group-membership Actions; usage location = Entra arm of `objects.user.update`, allow-listed to the single key `usageLocation` (TM-D28 B2/B4/B8); licence = `m365.licence.assign` / `m365.licence.remove`. **No `m365.group.member.*` and no `m365.user.usage_location.set`** (round 1 drafted them; superseded).
- **New persisted entities (domain-model follow-ups):** a **HybridRequest / continuation** record owned by `objects` (write-once digest columns, FR-17 D3; gate state, recorded anchor, activation digest, `approval_valid_until`, wait deadlines, `wait_reason`); **LicenceSku** inventory (SKU id, friendly name, service plans, prepaid/consumed units, observed time) — DM-16 has no licence concept beyond "Entra-only attributes (licences)"; Entra inventory rows and delta cursors ([e2-7a](e2-7a-entra-inventory-sync.md)); DM-21 attributes `sync_client`, `expected_sync_interval`, `source_anchor_attr`; DM-50 `usage_location` field and the deferred cloud step group.
- **Connector contract:** Entra rows of the EP-11 `(ProviderKind, WriteKind)` table with a `PropertyWrite` per kind (§8.9) for licence assignment, group membership add/remove and usage-location update (`WriteKind` has no Entra kind today, §8.1), with touched-set rule, conformance cases and a `Describe` entry; a retryable "target not yet visible" error (today `OBJECT_NOT_FOUND` is never retried); an ambiguous-outcome signal for Graph writes.

Verification, sync and waits are jobs, not requests.

## 10. Security considerations (tag all build tickets `security-sensitive`)

- **Privileges.** Entra: only FR-04's permissions, application-only, no directory role (EV3 refuses, no acknowledgement). Default grant = reads + `GroupMember.ReadWrite.All` + `Policy.Read.ConditionalAccess`; the membership write is tenant-wide for ordinary groups, so it is bounded by the allow-list, the Conditional Access designation and the restricted-management-AU guidance (FR-41), not by the permission (residual to be added to TM §6.6). Direct licensing and usage location are opt-in; `User.ReadUpdate.All` is tenant-wide profile write and is probably able to write `onPremisesImmutableId` and the UPN of non-admin users `[UNVERIFIED — lab G3 extended]`, which is why it is off by default (residual to be added to TM §6.6). AD: none new in this spec; the AD half's rights belong to E2.2/forest connection. `security-architect` re-reviews FR-03…FR-07, FR-13…FR-18, FR-24, FR-25, FR-33, FR-39, FR-41 and §14.1.
- **Tier 0.** Entra `tier0` (TM §6.4 E1–E5 and the TM-D25 reach closure) is outside every write scope (DM-35.I5). A new hybrid user is never `tier0` at creation, but may become so during the wait (a protected-group addition): the guard re-runs before each write (FR-16). A correlation never brings a `tier0` object into reach (DM-20.I7).
- **The central abuse case: licensing or grouping an object we did not create.** Vectors and defences: *soft match* (pre-staged UPN) — anchor-only lookup, attested soft-match blocking, writes by object `id`; *hard match* (pre-staged `onPremisesImmutableId` equal to the new GUID, readable by any domain user once the AD half commits, TM §6.8) — attested hard-match blocking plus FR-15's `anchor_on_cloud_object` hold, `cloud_seen_at` and alert, so DM-20.I4(g) fires; *anchor collision / stamped `ms-DS-ConsistencyGuid`* — anchor = our created `objectGUID`, `anchor_tampered` hold, Plan refuses the write, `ad_ref` binding, fail-closed I1a lookup; *flag flip in the wait window* — change monitoring (FR-06) and (g); residuals TM-R11, TM-R12 and the E4 admin who can write the anchor. An Entra-scoped admin acting on a `candidate` object is accepted by design (FR-32) and is unreachable from the continuation (FR-16).
- **Unattended continuation.** Bounded by the FR-17 table: bound descriptor, 24-hour fixed `approval_valid_until`, live re-check of initiator **and each approver**, no fall-through, Resume after expiry needs a new approval. This applies security ruling A.1, with the two-stage hash accepted on conditions D1…D6 (FR-17), a Resume that supersedes and never re-arms (FR-18), and sticky security holds (FR-35).
- **Safe primitives (rule 5).** OData through P8 only (`Eq`, `Str`, `Key(GUID)`; `MaxString`, `MaxIn`, `MaxAnd`, `MaxURL` limits); no Graph URL assembled outside `internal/directory/graphwrite`/home packages (FF-SP2/3: `graph-url-assembly`, `odata-key-shape`); JSON bodies from typed structs; objects addressed by `id` after `Unique`. The usage-location Action emits only the constant key `usageLocation`. Egress: one client, resolved IP, no private ranges (TM-TB9-T1); Graph host pin.
- **Credentials.** Certificate private key sealed, never returned, deleted when the connection is removed or the old key's thumbprint is gone after rotation (FR-39). An expired or extra credential on the app is a finding (EV5/EV3). A stolen certificate is a TM §6.6 residual (`addKey` mitigations).

## 14. Follow-ups (outside this diff; for the server board)

### 14.1 ADR-0005 amendment (technical, director-ratified): pointer list

One dated amendment written by `solution-architect` (ADR-0005 is ratified, so an amendment is allowed; no CEO decision). The amendment holds the text; this spec holds the product contract. It must contain:
1. **Coupled item group**: all-or-nothing blocking at Plan; a failed predecessor item sends its successor `planned → cancelled`.
2. **Wait step** (the product word stays "gate"; step kind `wait`, seam `Descriptor.Waits`, type `WaitCondition`, because ADR-0005 already has a `Gate` interface for the rule 8 approval gate, H3-n1) with a `waiting` state whose condition is **declared on the Action descriptor by the owning module** (§8). O5 (registry completeness) gains one case: a declared wait has an evaluator. Gate pass *binds* the resolved target and computes a read-only diff; a differing diff is the step-level wait reason `replan_changed`, not a rule 8 kernel hold. **A gate in a declared wait state holds no step claim and is exempt from stalled detection (rule 6 `operation.sweep`): it is stalled only past its deadline;** the sweeper drives the deadline, a scheduled poll drives the re-check.
3. **Outcome names inside the closed sets**: `partially_succeeded` widened to "an item succeeded and another failed, was blocked or was cancelled"; `cloud_reason` ∈ {`cloud_step_failed`, `cloud_expired`, `cloud_cancelled`, `cloud_denied`, `cloud_superseded`}.
4. **Resume** as a new Operation that ends a live original as `cloud_superseded` in one transaction; approval carry-over only after `cloud_step_failed` (rule 8 addition), FR-18. **Resume window rule (A3-m1 = H3-m1, `security-architect` confirms):** Resume always copies `objectGUID` and the anchor and never re-reads them; on carry-over it also copies `approval_valid_until` and the digest; a *new* approval writes a fresh `approval_valid_until` (capped by D6 from the new approval's time) and a fresh digest, once, in a new write-once row (D2, D3), with its own `objects.hybrid.awaiting_sync.started`; never an UPDATE. Test `resume_with_new_approval_writes_fresh_row_copies_identity`.
5. **Deferred target, hash and tokens** (rules 2, 9): activation digest rules D1…D6, FR-17.
6. **Plan-time authority** for a not-yet-existing Entra object (rule 7) and the approver re-check at Apply (rule 8).
7. **`plan_valid_until`** (1 h) governs queueing the AD item only; the cloud item is governed by `approval_valid_until`.
8. **Audit kinds** `objects.hybrid.*` and `connection.certificate.rotated`, registered by their owners (rule 1, EP-7).

Fitness tickets (an amendment is `accepted` only with its fitness function in CI): **FIT-1** `backend-engineer`, depends on the amendment: ADR-0005 O4, the `transitions` block and its property test (`planned → waiting`, `waiting → verified | not_run`, item `planned → cancelled`, gate-driven `running → cancelled`, wider `partially_succeeded`). **FIT-2** `backend-engineer`, depends on FIT-1: O8 cases for coupled blocking, gate expiry, sweeper exemption, Resume supersede and carry-over refusal.
