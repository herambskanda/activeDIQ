# Standard: CI gates and `make ci`

**Rule.** `make ci` is the one command that must pass before anything merges. The dispatcher runs it on the
merge result before every merge (the pre-merge gate, T-0941, below). A gate is not a gate until a deliberate violation makes it fail:
`make ci-proof` (part of `make ci`) keeps every gate honest by running it against a violation and
against clean input.

## The pre-merge gate (T-0941)

Until T-0941 nothing ran `make ci` at merge: the dispatcher's merge was a bare `git merge`, and a
worker's own `make ci` ran on its branch, not on the merge result. ADR-0001 and ADR-0002 named a
"dispatcher pre-merge gate (T-0015)", but that id became the Go upgrade and no ticket built the gate.
So `fitness-profiles` was red on `main` (6 findings at the T-0104 merge, 88 at the T-0555 merge) and each
of those merges still added findings: T-0104 took it from 6 to 8 (activation rows P2, P6 for
`packaging/windows/`), T-0555 from 88 to 90 (U3, U4 for `proto/skenzeriq/agent/`).

What the dispatcher does now for a finished code ticket (`factory/lib/premerge.mjs`, config
`dispatcher.pre_merge`):

1. Builds the merge result (`main` plus the branch) in a scratch worktree and runs `make -k ci` there.
   `-k` keeps going after a failure so every red job is seen.
2. Green: merge. A merge conflict: reopen the ticket as before.
3. Red and `main` green: refuse. Everything the run reports is new.
4. Red and `main` red: take the findings of the same command on `main` (a cached run, see **The baseline** below; a fresh run only when none stands for the current tree), compare **findings**
   as a multiset and refuse only if the merge result has one `main` does not. A finding is the check
   and message with the line and column, durations and the worktree path removed, so an old finding
   that moves does not count, a second copy of an old one does, and a job that turns red counts as the
   finding `FAILED <target>`. A run that fails with no recognisable finding line is refused.
5. A refused ticket returns to `in_progress` for its owner with the findings and the log paths in the
   note. If the gate cannot judge (timeout, worktree failure, a scratch tree removed or replaced while
   the command ran) nothing merges and it is retried after 10 minutes.
6. Every run, dry or real, has its own scratch tree and log (a per-run tag in the name), so runs that
   overlap cannot delete each other's tree. A truncated run is never judged or cached as `main`'s
   baseline (T-0696).

**The baseline (T-1378).** On 2026-11-02 the baseline was cached per full `main` sha, so every memory or docs commit on
`main` (several an hour) forced a fresh two-hour `make -k ci` on a loaded host, the baseline timed out three times and the
M1 queue stood still. The gate now (`baseline()` in `factory/lib/premerge.mjs`): (1) reuses a cached run on the same tree;
(2) reuses the newest cached run whose tree differs from `main`'s only in files under `knowledge/`, `.claude/`,
`factory/`, `garage/` that no gate file mentions as a path (`readSurface`: path literals and joined literals such as
`filepath.Join(root, "knowledge", "development", "decisions")` in every tracked non-prose file outside those
directories, computed from the tree on each gate, not listed by hand); (3) stores the merge-result run of a passing gate
as the baseline of the tree it becomes, so the second half of a split train needs none; (4) when a fresh baseline times
out, lets the nearest cached run clear the merge result (all findings known) but never refuse it, and otherwise stops
naming the findings. The reuse is safe because the head run always executes on the real current `main` plus the branch:
a stale reference can only make an unrelated finding look new (a refusal that names it), not hide one. The gate summary
states `baseline: reused the cached run …` or `baseline: ran a fresh baseline …`.
Fitness: `factory/test/premerge.test.mjs` (reuse, no reuse for each read path class, the read surface, seeding, timeout fallback).

**Merge train (T-1297).** One gate run takes 40-75 minutes, so judging one ticket per run merged about one ticket
an hour while about five an hour reached `done` (26 → 41 done-unmerged on 2026-11-02). The gate now judges a
*train*: up to `dispatcher.pre_merge.train_size` (default 4) tickets from the front of the queue (T-1296 order),
merged one after another onto `main` in the scratch worktree (`runPreMergeTrain`), then the numbering check and
`make -k ci` once on the combined result. The rules in steps 1-5 above apply to the combined result unchanged.

- Green or ratchet-pass: each member merges into `main` in queue order, one `--no-ff` merge commit each.
- Refused: the gate cannot say which member is at fault, so the train is split in halves (`splitTrain`); the first half
  is gated and merged, then the second is gated on the new `main`, recursively. A ticket that is alone in its train
  and refused is reopened with the findings and logs exactly as before; the others merge. Worst case about
  2·log2(N) extra runs for one bad ticket, against N runs for one-at-a-time.
- A member that conflicts in text with an earlier member is left out and stays `done` for the next train; one that
  conflicts with `main` itself is reopened as before.
- Could not judge (timeout, worktree failure): nothing merges and all members retry after 10 minutes.
- Logs: `state/premerge/train-T-a+T-b+….log` for a train of several, `T-….log` for one.

Fitness: `factory/test/mergetrain.test.mjs` (runtime tests against a real temp git repository; the bisection tests fail
if the split is removed).

**Migration numbering (T-1067).** Before the full command the gate runs a cheap check on the same merge
result (`dispatcher.pre_merge.numbering`: `go test ./migrations/ -run ^TestMigrationNumbersAreUniqueAndContiguous$`,
no database, about 1 s warm). Two parallel branches that each add `00NN` pass that test alone and collide only
once merged; four such collisions reached `main` (0034/0035 T-0505, 0047 T-0597/T-0608, 0061 T-1066), and the
full-run ratchet could not be relied on to catch it while `main` was red. A failure refuses the merge
before `main` moves and reopens the ticket with `Renumber to NNNN: git mv …`, the number being the next free
one on current `main`. It is judged absolutely, not against `main`'s baseline, and a check that cannot run
(timeout, no `go`) throws like any other gate failure. Test: `factory/test/premerge-numbering.test.mjs`.

A finding line is recognised by shape (`findingKey` in `factory/lib/premerge.mjs`; line numbers,
durations, scratch paths and the worktree path are not part of the key):

| Shape | Printed by |
| --- | --- |
| `path:line[:col]: message` (also `P1 (ADR-0002 fitness function): …`) | profiles, safeprim, modules, operation, api, proto, objectid, grantbootstrap, disclosure |
| `<where>:line <check> [<rule>]: message` | fleetca, reports, keycustody, the bound-test failures |
| `<check> <where> [<rule>]: message` | tenancy, audit, domainkeys |
| `<where>: <check> [<rule>]: message` | corpus |
| `<file or dotted name>: message`, no line (`go.mod: F4 (ADR-0001 rule 4): …`, `<scenario>/<case>: …`, `attr.sid: FF-SP6 …`) | stack, api A5, tenancy OpenAPI, packaging, disclosure, update, oracles |
| `fitness-x: FAIL: …` / `fitness-x: <message>` | sso, built-msi, update-offline |
| a heading `<id> <what>: FAIL` or `FAIL <case>`, then one indented line per violation (key `FAIL <id>: <line>`; a `GAP` heading is a tolerated gap, not a finding) | agent-host, host |
| a failed make target, `--- FAIL`, `FAIL pkg` | any |

Progress and summary lines (`ok`, counts, `inactive`, `pending`, `PostgreSQL 16 (…)`) are not findings.
A job that prints violations in none of these shapes is red on `main` but not ratcheted: new
findings in it pass while it is red. So every job of `make fitness` has a sample violation line in
`JOBS` in `factory/test/premerge.test.mjs`; a test fails when a job of the target has none, and one
run through the gate per shape shows a violation added to a red job is refused naming it. A new
fitness tool adds its line there, and prints one self-contained line per violation. A new shape goes
into `findingKey` (or, for a heading with indented violations, `FAIL_BLOCK`) in `extractFindings`.

Dry run, changes nothing: `factory/bin/factory premerge T-NNNN` (or `… -- make fitness-profiles` to
run one job). On a red `main` with no cached baseline it runs `make -k ci` twice and can outlast a
worker's 90-minute run budget, so run it in the background (T-1217). Tests: `node --test factory/test/premerge.test.mjs`. Runbook: `runbooks/ci-and-build.md`.

## Rules for adding a gate

1. Add it to `tools/ci/ci.mk` under `ci`. Never `-` prefix a recipe line, never `|| true`, never
   `continue-on-error`.
2. Add its failing and passing case to `tools/ci/proof.sh`, using `must_fail_with` so it fails for the
   expected reason, not because a tool is missing.
3. Add any new tool to the licence register first (CLAUDE.md rule 9) and pin its version.

## `fitness-stack` in one page (T-0022)

Rules and rationale: ADR-0001 (`accepted`; its fitness function is this job). Every message reads

| Check | Rule | What it reads | Notes |
| --- | --- | --- | --- |
| F1 | 1 | tracked and untracked-unignored files | An allowlist per zone (`languageZones` in the manifest). Extensionless scripts are classified by shebang. `.js/.mjs/.cjs` count as JavaScript and live only under `web/`. A `native/` crate must be a manifest-declared tier-N Windows component, which keeps PAM and macOS logon code out until their ADR exists |
| F2 | 2 | `go/parser` (imports and comments, never string contents), `go/build/constraint`, a text scan of every non-prose file, `go build` per target | Files under `//go:build ignore` are still scanned. `unix` counts as a GOOS.
