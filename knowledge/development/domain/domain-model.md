# activeDIQ domain model v0

The shared vocabulary every feature lands on. Each entity has an ID (`DM-nn`) and numbered
invariants (`DM-nn.In`) so specs, tickets and tests can cite them ("violates DM-16.I2").
It restates and does not override [ADR-0002](../decisions/0002-deployment-model.md) (tenancy) or the
[blueprint](../architecture/blueprint.md) (components). Where they disagree, the ADR wins and this
file is the bug. Table shapes, indexes and partitioning are decided by the owning build tickets
and T-0026. This file fixes **what exists, what is always true, and how it moves**.

**Kinds.** `P` platform scope: a registered-global table (ADR-0002 rule 4), set by the
installation operator. `T` tenant scope: `tenant_id` plus forced RLS, set only through the public
API. `D` directory-observed: tenant scope, written only by `sync` or by an Action's verified
outcome, and read-only to everything else. `R` registry: declared in code through the
`Registrar` (blueprint §4.1). It is not a table, but persisted data references it by ID.
**Owner** is the package that owns the entity's tables (blueprint §2 rule 6).
**`[LAB: Windows]`** marks AD behaviour that Microsoft documents (cited inline) but that we have
not yet reproduced against a Windows DC. Code must not rely on such a claim until a lab test has
confirmed it (T-0051, §11 Q8).

## 0. Invariants for every entity

- **X1 Tenancy.** Every `T`/`D` row has `tenant_id`. It leads the PK and every unique index, and
  every FK to a tenant table is composite (ADR-0002 "Where tenancy lives"). No entity references
  another tenant's row. `P` rows never reference a `T` row.
- **X2 Surrogate IDs.** These are UUIDs generated by the application. Row IDs are time-ordered
  (v7), and tenant IDs are random (v4, ADR-0002 rule 5). Directory identities are the directory's
  own GUIDs (X3), never surrogates.
- **X3 Directory identity.** A directory object is `(connection_id, object_guid)`: the AD
  `objectGUID` or the Entra object `id`. A DN, SID, sAMAccountName or UPN is never a key, FK or
  join column. DNs change on rename and move, and SIDs change on a cross-domain move
  ([objectGUID](https://learn.microsoft.com/en-us/windows/win32/adschema/a-objectguid),
  [sIDHistory](https://learn.microsoft.com/en-us/windows/win32/adschema/a-sidhistory)). Every
  reference column holds a GUID. Display strings (DN, name) are stored as *snapshots* beside it.
- **X4 Secrets never persist in clear.** Passwords, OTP codes, LAPS/BitLocker values and
  `SecretAttrs` (safe-primitives §3.7) are never stored. The exceptions are credentials and seeds,
  which are stored *sealed* under the tenant data key. No `Secret` is ever serialised into an
  entity, an audit detail, a notification or an export.
- **X5 Append-only records** (ChangeRecord, AuditEvent, ApprovalDecision, ChainCheckpoint) are
  never updated. Only retention deletes them, and only as an explicit, audited path.
- **X6 Registry IDs are stable strings, never reused.** A persisted reference to a registry entry
  (Permission, Action, Dataset, audit kind, job kind) blocks that entry's removal until a
  migration rewrites the reference.
- **X7 Definitions are versioned; runs pin versions.** Templates, naming formats, workflow
  definitions, automation policies and report definitions publish immutable versions. Every
  Operation, Request, AutomationRun and ReportRun records the version it used.
- **X8 Time** is `timestamptz` in UTC. A schedule's time zone is data (DM-44). FILETIME values are
  converted at the codec (P3).
- **X9 Every directory write is an Operation** (DM-41) executing a registered Action (DM-40). No
  entity offers a side door: templates, automations, workflows, report results and ITSM tickets
  all *produce* Operations.
- **X10 Our records outlive the directory's.** Deleting an object, connection or account never
  deletes our audit trail. Retention is a tenant setting per record class (ADM-206).

**Lifecycle notation.** `a → b` is a transition. `a ⇄ b` is reversible. A *state* is persisted;
*health* (reachable, degraded, lagging) is observed, shown, and never a lifecycle state.

```
 PLATFORM  Tenant(1) Node Release HostnameBinding Lease(platform)

 Directories: Connection --< NamingContext --< DomainController      Connection --< ConnectorBinding >-- Component

```

## 1. Platform and tenancy

### DM-01 Tenant · P · owner `platform/tenant`
**Definition.** The isolation boundary for all customer data. A self-hosted install has exactly
one; a SaaS cell has many. **Replaces (ME):** none (ADMP is single-organisation).
**Key attributes:** `id` (random UUID) · `parent_tenant_id` (null in v1) · `name` · `state` ·
`placement` (cell, database; SaaS only) · `region` · `created_at` · `state_changed_at`.
**Invariants.** I1 A self-hosted install has exactly one tenant, created by the installer. There
is no default-tenant constant (ADR-0002 rule 5). I2 `tenant.ID` is minted only by authn, the job
wrapper, registered platform paths and tests. It comes from an authenticated principal, never from
request content. I3 `parent_tenant_id` references an existing tenant and the graph is acyclic.
RLS never admits a parent into a child's rows; MSP work iterates tenants under a grant (E5.6).
I4 Each tenant has exactly one audit hash chain (DM-80) and one active data key (DM-02).
I5 Deletion shreds the tenant's keys before rows are purged. Only the `id` and timestamps survive,
in the `deleted` row.
**Lifecycle.** `provisioning → active ⇄ suspended → deleting → deleted`. Self-hosted tenants are
created `active`, because the `tenant-provisioning` capability is not composed there. While
`suspended`: sign-in is refused, jobs are paused and connectors are refused; data is kept. The
export window during `deleting` is `[OPEN → E5.6]`.

### DM-02 TenantKey · T · owner `platform/keys`
**Definition.** A tenant's data-encryption key, wrapped by the installation KEK from the profile's
key provider. Everything sealed (DM-11, DM-37, DM-63, DM-82, DM-85) is sealed under it.
**Key attributes:** `version` · `wrapped_dek` · `kek_ref` (provider, key id) · `state` · `created_at`.
**Invariants.** I1 Exactly one `active` version per tenant. I2 Every sealed value records the key
version that sealed it. I3 The plaintext DEK exists only in memory. I4 Shredding destroys every
version. The rotation procedure is `[OPEN → T-0007]`.
**Lifecycle.** `active → retired` (decrypt-only) `→ shredded`.

### DM-03 Node · P · owner `platform/update` (registry of server processes)
**Definition.** One running `server` process of the installation. Nodes are stateless, and HA is
achieved by adding them (ADR-0002 rule 6). **Replaces (ME):** primary/standby HA and load-balancer
nodes (ADM-210).
**Key attributes:** `id` · `hostname` · `version` · `roles` · `started_at` · `last_heartbeat`.
**Invariants.** I1 A node holds no state that another node needs. I2 A node whose heartbeat has
expired loses its leases (DM-06). I3 Only a node running the current Release's version may take
the migration lease.
**Lifecycle.** `joining → active → draining → gone`.

### DM-04 HostnameBinding · P · owner `platform/apihost`
**Definition.** It maps a public hostname to a tenant for **anonymous end-user flows**: in v1 the
TOTP enrollment page (FD-05), and SSPR from M4.
**Key attributes:** `hostname` (lower-case, IDNA) · `tenant_id` · `capabilities` (closed set of
anonymous flows) · `state`.
**Invariants.** I1 One hostname maps to one tenant. I2 It grants only anonymous-flow
capabilities, never console or API access (ADR-0002 Request row).
**Lifecycle.** `active ⇄ disabled → deleted`.

### DM-05 Release · P · owner `platform/update`
**Definition.** A signed release manifest that the installation has seen, with its apply history
(ENH-07). **Replaces (ME):** service packs and automatic hotfixes (ADM-209, ADM-213).
**Key attributes:** `version` · `manifest_digest` · `signing_key_id` · `courier` (online,
offline) · `state` · `applied_at` · `rollback_reason`.
**Invariants.** I1 Only a verified release can be staged. Both couriers use one verifier
(ADR-0002 rule 7). I2 At most one release is `applying`, under the migration lease. I3 Migrations
are expand-only. I4 Rows are never deleted.
**Lifecycle.** `discovered → verified | rejected`, then `verified → staged → applying → applied |
rolled_back`.

### DM-06 Lease · P (platform work) and T (tenant work) · owner `platform/jobs`
**Definition.** Exclusive, expiring ownership of singleton work: the sync reader per partition,
schedulers and migrations. One shape, two tables: platform leases are global, tenant leases are
under RLS.
**Key attributes:** `resource_key` · `holder_node` · `fencing_token` (monotonic) · `expires_at`.
**Invariants.** I1 At most one holder. I2 Writes made under a lease carry its fencing token. For
example, a SyncCursor write is refused if the token is stale.
**Lifecycle.** `free → held → (renewed) → released | expired`.

## 2. Directories

### DM-10 Connection · T · owner `modules/connections` (model in `directory/model`)
**Definition.** One directory activeDIQ manages: an **AD forest** or an **Entra tenant**. Each
connection has its own credential, bindings and sync. **Replaces (ME):** the "domain" in Domain
Settings (ADM-212; per-domain settings move to DM-14) and the M365 tenant configuration (ADM-159).
**Key attributes:** `kind` (`ad_forest`, `entra_tenant`) · `display_name` · `directory_identity`
(AD: the objectGUID of the forest root domain NC, read from the root domain's crossRef `nCName`
as an extended DN, with the forest root domain SID as a second check; Entra: the tenant ID) ·
`forest_dns_name` and `forest_netbios_name` (snapshots: a domain rename keeps the GUID,
[domain rename](https://learn.microsoft.com/en-us/previous-versions/windows/it-pro/windows-server-2008-R2-and-2008/cc816795(v=ws.10))) ·
forest-wide deletion settings (AD only): `recycle_bin_enabled`, `tombstone_lifetime_days`,
`deleted_object_lifetime_days` · `verified_at` · `transport_security` (LDAPS or StartTLS) ·
`dc_affinity` (site priority, per-OU preferred DCs, ADM-133) · `sync_attribute_set` (additions to
the default set) · `credential_id` · `state`.
**Invariants.** I1 `directory_identity` is fixed at first verification. A connection cannot be
re-pointed at another forest or tenant, because that would mix two directories' GUID spaces.
I2 `(kind, directory_identity)` is unique per tenant. I3 An `active` connection has at least one
binding (DM-13). I4 The security floor is not configurable downward: TLS, signing, sealing and
channel binding are always on (ADR-0002 rule 8). I5 Removal never deletes audit events (X10).
Inventory is purged by retention. I6 The deletion settings are read from the directory and never
assumed. They are forest-wide, so they live here and not on NamingContext. An absent
`tombstoneLifetime` means 60 days; 180 is written only when the forest was created on WS2003 SP1
or later ([tombstoneLifetime](https://learn.microsoft.com/en-us/windows/win32/adschema/a-tombstonelifetime)).
An absent `msDS-deletedObjectLifetime` means it equals the effective tombstone lifetime
([ADAC L200](https://learn.microsoft.com/en-us/windows-server/identity/ad-ds/get-started/adac/advanced-ad-ds-management-using-active-directory-administrative-center--level-200-)).
**Lifecycle.** `draft → verifying → active ⇄ suspended → decommissioning → removed`. Verifying
checks reachability, identity and the delegated-rights limit (T-0007, ENH-08). Suspended stops
sync and writes.

### DM-11 DirectoryCredential · T · owner `connector/credential` (metadata row owned by `modules/connections`)
**Definition.** The identity a connection uses against its directory. **Replaces (ME):** the
domain service-account and M365 app credentials, stored with AES-256 in ADMP
([data-security PDF](https://download.manageengine.com/products/ad-manager/encryption-and-data-storage-in-admanager-plus-database.pdf)).
**Key attributes:** `kind` (`gmsa`, `keytab_ref`, `ad_password`, `entra_certificate`,
`connector_local`) · public metadata (account or principal name, SID, Entra app/client ID, cert
thumbprint, `not_after`) · `sealed_secret` (only for `ad_password` and the Entra private key) ·
`key_version` · `state`.
**Invariants.** I1 Only code under `internal/connector/` unseals or uses it. API responses carry
metadata only (ADR-0002 rule 3, P3). I2 `gmsa` and `keytab_ref` hold no secret in the database.
`connector_local` means the secret lives on a remote connector's host. A SaaS AD connection is
always `connector_local`. I3 activeDIQ generates the Entra private key; the admin uploads only the
public certificate. I4 Rights are delegated only, with no Tier-0 or Entra privileged-role rights
(ADR-0002 rule 9).
**Lifecycle.** `pending` (key generated, awaiting consent or rights) `→ active → expiring`
(`not_after` within the reminder window) `→ rotated` (superseded) `| revoked`.

### DM-12 Component · T · owner `platform/fleet`
**Definition.** An enrolled remote process with its own mTLS identity. In v1 that is a remote
**connector**; from M3 also an **agent**. The embedded connector has no identity and is not a
Component (ADR-0002). One shape covers both kinds ("parameterise, don't clone").
**Key attributes:** `kind` (`connector`, `agent`) · `name` · host facts (hostname, OS, version) ·
`cert_serial` · `san_identity` (tenant + component) · `providers` (from `Describe`) ·
`server_endpoints` · `last_seen` · `state`. Sub-entity **EnrollmentToken**: `token_hash`,
`issued_by`, `expires_at`, `used_at`.
**Invariants.** I1 Enrolled to exactly one tenant. The tenant comes from the certificate, never
from a message. I2 An enrollment token is single-use, expiring, stored hashed, and issued by an
account holding the enrollment permission. I3 Certificate rotation keeps the Component identity.
**Lifecycle.** `pending` (token issued) `→ enrolled → active → revoked → removed`. Reachability is
health.

### DM-13 ConnectorBinding · T · owner `modules/connections`
**Definition.** It routes a connection to the connector(s) that serve it. The binding is data, not
configuration (ADR-0002 rule 3). **Replaces (ME):** none (ADMP has no distributed connectors).
**Key attributes:** `connection_id` · `target` (`embedded` or a `component_id`) · `priority` · `state`.
**Invariants.** I1 Target and connection belong to the same tenant (composite FK). I2 A binding
is accepted only if the target's `Describe` reports a provider for the connection's kind. This is
why SaaS AD connections can never bind `embedded` (ADR-0002 P1). I3 Several bindings give
redundancy (ADM-210). Each operation item keeps one DC and one connector (read-your-writes).
**Lifecycle.** `active ⇄ disabled → removed`.

### DM-14 NamingContext · D · owner `directory/inventory`
**Definition.** A partition of an AD forest. **Domain** NCs hold managed objects. The
configuration and schema NCs are read for topology and the schema cache only. The equivalent for
an Entra connection is the tenant itself, so it has no NamingContext rows. **Replaces (ME):** a
managed "domain" (ADM-212, ADM §2.9).
**Key attributes:** `nc_guid` (NC head objectGUID) · `kind` (domain, configuration, schema,
application) · `dns_name` and `netbios_name` (snapshots) · `domain_sid` · `functional_level` ·
`managed`.
**Invariants.** I1 Only domain NCs can be `managed`. I2 Deletion lifetimes and the Recycle Bin
flag are forest-wide and live on the Connection (DM-10.I6), never per NC.
**Lifecycle.** `discovered → managed ⇄ unmanaged → gone`.

### DM-15 DomainController · D · owner `directory/inventory`
**Definition.** A DC of a managed domain, as discovered from the configuration NC and DNS.
**Key attributes:** `dsa_guid` (objectGUID of its NTDS Settings object; the stable DC identity) ·
`invocation_id` (replication identity; changes on restore and when the VM-GenerationID changes,
[virtualized DC](https://learn.microsoft.com/en-us/windows-server/identity/ad-ds/get-started/virtual-dc/virtualized-domain-controller-architecture)) ·
`dns_hostname` · `site` · `is_gc` · `is_rodc` · `os_version` · admin flags (`excluded`,
`priority`) · `last_seen`.
**Invariants.** I1 Per-DC values (e.g. `lastLogon`, ADM-084) are keyed by `dsa_guid`.
I2 An RODC is never a write target. I3 An operation item's apply and verify use the same writable
DC. I4 Demoting and re-promoting a server creates a new NTDS Settings object, so it is a **new**
DC row with a new `dsa_guid`, even under the same hostname. I5 Any USN-based position is keyed by
`(dsa_guid, invocation_id)`. A changed `invocation_id` invalidates it.
**Lifecycle.** `discovered → in_use | excluded → retired`.

### DM-16 DirectoryObject · D · owner `directory/inventory`
**Definition.** The current, last-observed state of one AD or Entra object: user, inetOrgPerson,
group, computer, contact, OU, container, gMSA, foreign security principal, or another class
carried as data. **Replaces (ME):** the objects behind every Management tab (ADM-008…062), AD
Explorer (ADM-004) and the M365 objects (ADM-160…164).
**Key attributes:** `object_guid` · `connection_id` · `nc_guid` · `object_class` (most specific
structural class) and `kind` · `parent_guid` · `ancestry` (GUID path to the NC head) · `dn` and
`rdn` (display snapshot) · `sid` (security principals) · `sam_account_name` · `upn` ·
`display_name` · `enabled` (from `userAccountControl`) · time-dependent state *inputs*:
`lockout_time`, `pwd_last_set`, `account_expires`, and the effective password policy (domain
policy or PSO) · `tier0` (definition: T-0007) · typed values of the synced attribute set ·
`when_created` · `when_changed` · `observed_at` + `observed_dsa` · `state`.
**Invariants.**
- I1 Identity is the GUID (X3). A rename, a move, or a cross-domain move within the forest changes
  `dn`, `parent_guid`, `ancestry`, `nc_guid` and, for a cross-domain move, `sid` (the old SID goes
  to `sIDHistory`). It never changes identity. A cross-domain move expunges the object from the
  source NC and leaves only an `infrastructureUpdate` proxy there
  ([cross-NC move](https://learn.microsoft.com/en-us/openspecs/windows_protocols/MS-ADTS/8bcbd10f-f98b-4881-84b0-290db509cc18)).
  So sync treats an add of a known GUID in another NC as a **move**, never a delete plus a create,
  and a resync diffs the whole forest by GUID, never one NC at a time `[LAB: Windows]`.
- I2 `dn` is display-only and is refreshed on every observation.
- I3 Secret attributes are never stored (X4, safe-primitives LF-38).
- I4 There is one current row per identity. Its past values live in ChangeRecord (DM-18).
- I5 Values carry freshness (`observed_at`, source DC). Last logon is per-DC or labelled with
  `lastLogonTimestamp`'s lag.
- I5a Time-dependent state is never stored as a flag. A lockout expiring or a password expiring
  involves no directory write, so sync never sees it, and `lockoutTime` is not reset to 0 when the
  lockout duration passes ([lockoutTime](https://learn.microsoft.com/en-us/windows/win32/adschema/a-lockouttime)).
  `locked_out`, `password_expired`, `password_expires_at` and `account_expired` are computed at
  read time from the stored inputs and the effective policy. A decision that acts on them (unlock,
  reset, a leaver policy) re-reads `msDS-User-Account-Control-Computed` and
  `msDS-UserPasswordExpiryTimeComputed` live at Plan `[LAB: Windows]`.
- I6 AD and Entra objects are never merged. A hybrid user is two rows joined by a Correlation
  (DM-20).
- I7 Uniqueness (sAMAccountName, UPN, CN in a container) is decided by the DC, not by this table
  (safe-primitives R9).
- I8 `tier0` objects are outside every write scope in v1 (DM-35.I5).

**Lifecycle (AD).**

```
 live --delete--> deleted --(msDS-deletedObjectLifetime)--> recycled --(tombstoneLifetime)--> purged
  ^                  |                                       (Recycle Bin on; isRecycled: never restorable)
  +----restore-------+   restore keeps objectGUID and objectSid; links and attributes come back
 live --delete--> tombstone --(tombstoneLifetime)--> purged      (Recycle Bin off)
  ^                  |
  +--reanimate-------+   keeps objectGUID, objectSid, sIDHistory and searchFlags-0x8 attributes; every link value is lost
 any --moved into an unmanaged NC / NC unmanaged--> out_of_scope --back in scope--> live
```

`purged` keeps the history rows and a final ChangeRecord. With the Recycle Bin, restored users
"regain all group memberships" ([Recycle Bin](https://learn.microsoft.com/en-us/windows-server/identity/ad-ds/get-started/adac/active-directory-recycle-bin)).
Restore rules `[LAB: Windows]`
([tombstone and recycled objects](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-adts/4302a2eb-55c8-426c-b310-6791c6ae8307)):
a recycled object (`isRecycled`) cannot be undeleted at all. A restore needs a live parent (the
object's `lastKnownParent`, or a restored one). An object deleted before the Recycle Bin was
enabled is a tombstone and only reanimates, with the losses shown above.
**Lifecycle (Entra).** `active → soft_deleted → purged`, and `soft_deleted → active` on restore.
Restorable for 30 days: users, Microsoft 365 groups (assigned and dynamic), cloud security groups
(preview, public clouds), applications, service principals and administrative units
([restore groups](https://learn.microsoft.com/en-us/entra/identity/users/groups-restore-deleted),
[deleted items](https://learn.microsoft.com/en-us/graph/api/resources/directory?view=graph-rest-1.0)).
Distribution groups are not restorable, so their delete goes straight to `purged`. activeDIQ restores a
synced object in AD, its source of authority, and never through Entra. Whether Entra deleted items
can restore a synced group at all is `[UNVERIFIED]`. In a delta feed, `@removed.reason: changed` maps to `soft_deleted` and `deleted`
maps to `purged` ([delta query](https://learn.microsoft.com/en-us/graph/delta-query-overview)).

### DM-17 Link · D · owner `directory/inventory`
**Definition.** One value of a linked attribute (`member`, `manager`, …), stored as a directed edge
between GUIDs. **Replaces (ME):** membership management (ADM-050) and the manager field (ADM-033).
**Key attributes:** `source_guid` · `link_attr` · `target_guid`, or `target_unresolved` (a SID for a
foreign security principal not yet resolved, or a DN outside every managed NC, as a snapshot) ·
`state` · `observed_at`.
**Invariants.** I1 Only forward links are stored. Back-links (`memberOf`, `directReports`) are
derived ([linked attributes](https://learn.microsoft.com/en-us/windows/win32/ad/linked-attributes)).
I2 The primary group is its own edge kind, derived from `primaryGroupID`, because it is absent from
`member`. I3 Group nesting may cycle, so every transitive traversal carries a visited set.
I4 A cross-forest member is an edge to a foreign security principal object. Resolving it to the
other forest's object is a lookup recorded on the edge, never a merge. FSPs also stand for
well-known SIDs such as Authenticated Users, which resolve to no object. A member from another
domain of the *same* forest is an ordinary DN value to a real object, never an FSP
([foreignSecurityPrincipal](https://learn.microsoft.com/en-us/windows/win32/adschema/c-foreignsecurityprincipal)).
**Lifecycle.** `active → deactivated` (target deleted with the Recycle Bin on) `→ active`
(restore), or `→ removed`. With the Recycle Bin off, a deleted target's links are removed, not
deactivated, and a reanimation does not bring them back `[LAB: Windows]`. Every transition writes
a ChangeRecord.

### DM-18 ChangeRecord · D · append-only · owner `directory/inventory`
**Definition.** One observed change to one attribute or link value of one object. This is the
history built for audit queries over years (blueprint §12). **Replaces (ME):** the object History
tab (ADM-005), and from M3 part of the Backup Explorer (ADM-150).
**Key attributes:** `object_guid` · `connection_id` · `attribute` (or link attr + target) · `old` ·
`new` · `observed_at` · `origin` (nullable: originating DSA invocationId, originating USN,
originating time and version, from `msDS-ReplAttributeMetaData` and
[`msDS-ReplValueMetaData`](https://learn.microsoft.com/en-us/windows/win32/adschema/a-msds-replvaluemetadata)) ·
`source` (`sync`, `operation:<id>/<item>`, or `event:<id>` from M3) · `actor` (only when the
source is an operation).
**Invariants.** I1 Append-only (X5). It is partitioned by time and retained per tenant
(ADM-206). I2 It is observation-based: a value that changed twice between two observations shows
as one change, and the UI says so. DirSync returns final state only, never old values, so `old`
comes from our previous observation. I2a `origin` is null for link values written before
linked-value replication was enabled (legacy values carry no value metadata)
`[LAB: Windows]`. The originating time is the originating DC's clock and is labelled as such,
never presented as our observation time. I3 v1 never attributes a native (non-activeDIQ) change to a
person. That arrives with DC events (M3). I4 Secret attributes are never recorded. I5 It is
indexed for three questions: everything about object X, every change to attribute A in a period,
and everything operation O did.
**Lifecycle.** `recorded → archived → purged` (retention).

### DM-19 SyncCursor · T · owner `directory/sync`
**Definition.** The change-feed position for one partition: an AD domain NC (DirSync) or one Graph
resource of an Entra tenant (delta).
**Key attributes:** `connection_id` · `partition` (NC GUID or Graph resource) · `cookie` (opaque) ·
`issuing_dsa_guid` (AD: the DC that issued the cookie) · `last_full_sync_at` · `last_change_at` ·
`lease_fencing_token` · `state`.
**Invariants.** I1 It is written in the same transaction as the inventory rows it covers
(blueprint §14 flow 1). I2 One reader per partition holds the lease (DM-06). I3 An invalid or
expired cookie forces a full resync. That resync diffs against inventory forest-wide by GUID
(DM-16.I1), so deletions missed while the cookie was stale still become `deleted` or `purged`.
I4 A DirSync cookie is reused only on the DC that issued it. On another DC it may replay changes,
return everything, or be rejected with `0000203D`. All three outcomes end in `resync_required`
([DirSync](https://learn.microsoft.com/en-us/windows/win32/ad/polling-for-changes-using-the-dirsync-control)).
I5 DirSync does not report the children of a moved or renamed parent. Their `dn` and `ancestry`
are re-derived from the parent's new position, not awaited from the feed. I6 A Graph delta token
expires after 7 days (`syncStateNotFound`), and `410 Gone` also means a full sync
([delta query](https://learn.microsoft.com/en-us/graph/delta-query-overview)). The AD reader
contract (show-deleted control `1.2.840.113556.1.4.417` with DirSync, an `objectClass` filter
rather than `objectCategory`, and `isDeleted` requested) belongs to T-0018.
**Lifecycle.** `initial_sync → incremental ⇄ resync_required`. It is `paused` while the connection
is suspended.

### DM-20 Correlation · D · owner `directory/inventory`
**Definition.** It asserts that an AD object and an Entra object are the same identity, and records
which side is the source of authority. **Replaces (ME):** the hybrid handling behind ADM-169.
**Key attributes:** `ad_ref` · `entra_ref` · `anchor_attr` (`objectGUID`, `ms-DS-ConsistencyGuid`,
or another attribute) · `anchor_value` · `source_of_authority` (`ad` when `onPremisesSyncEnabled`
is true, unless `onPremisesSyncBehavior.isCloudManaged` is true, which makes Entra the master;
that property is beta,
[onPremisesSyncBehavior](https://learn.microsoft.com/en-us/graph/api/resources/onpremisessyncbehavior)) ·
`match` (`anchor`, or `sid` via `onPremisesSecurityIdentifier`) · `state`.
**Invariants.**
- I1 A correlation is made only from the source anchor or the SID, never from name or UPN
  heuristics ([sourceAnchor](https://learn.microsoft.com/en-us/entra/identity/hybrid/connect/plan-connect-design-concepts)).
  For users, `onPremisesImmutableId` is the base64 of a binary anchor (objectGUID,
  ms-DS-ConsistencyGuid). A string anchor such as employeeID is used as is.
- I1a Users match `ms-DS-ConsistencyGuid` first, then `objectGUID`. After a forest migration the
  anchor can be the *old* forest's GUID, carried in ms-DS-ConsistencyGuid. With the ConsistencyGuid
  option, Entra Connect uses ms-DS-ConsistencyGuid for users and objectGUID for other types. Cloud
  Sync uses ms-DS-ConsistencyGuid when present, else objectGUID, and that choice cannot be changed
  ([Cloud Sync topologies](https://learn.microsoft.com/en-us/entra/identity/hybrid/cloud-sync/plan-cloud-sync-topologies)).
- I1b Groups have no `onPremisesImmutableId`. They match on `onPremisesSecurityIdentifier` (the AD
  group's SID) ([group](https://learn.microsoft.com/en-us/graph/api/resources/group?view=graph-rest-1.0)).
  A cross-domain move changes the SID (DM-16.I1), so the correlation goes `broken` until
  `onPremisesSecurityIdentifier` carries the new SID. It is never re-matched by name.
- I2 There is at most one Entra object per AD object per Entra tenant.
- I3 Writes to attributes whose source of authority is AD go to AD; Entra-only attributes
  (licences) go to Graph.
**Lifecycle.** `matched ⇄ broken` (one side purged, or an anchor or SID mismatch; it returns to
`matched` only through I1) `→ removed`.

### DM-21 HybridLink · T · owner `modules/connections`
**Definition.** It declares which AD domain syncs into which Entra tenant. The relation is
many-to-many. **Replaces (ME):** the domain↔tenant links (ADM-159).
**Key attributes:** `ad_connection_id` + `nc_guid` · `entra_connection_id` · `origin` (declared,
or discovered from correlations) · `state`.
**Invariants.** I1 It decides which Entra tenant receives the M365 steps of a user create
(ADM-027).
**Lifecycle.** `proposed → confirmed → removed`.

### DM-22 Snapshot · T · owner `modules/history`
**Definition.** A point-in-time copy of inventory for one connection, used as the baseline and
rollback point (MIG-18).
**Key attributes:** `connection_id` · `scope` (NCs) · `attribute_set` · `reason` (baseline,
scheduled) · `object_count` · `blob_ref` (tenant-prefixed) · `checksum` · `state`.
**Invariants.** I1 Holds no secret attributes. I2 Immutable once `complete`. I3 Restoring from a
snapshot is an Operation (X9).
**Lifecycle.** `capturing → complete | failed`, then `complete → expired → deleted`.

## 3. Identity and access

### DM-30 Account · T · owner `platform/authn`
**Definition.** A human who signs in to the console or API: a technician, an administrator or a
workflow requester. **Replaces (ME):** the technician (ADM-126) and workflow requester accounts
(ADM-117).
**Key attributes:** `kind` (`local`, `sso` with issuer+subject, `directory` with
connection+GUID) · `display_name` · `email` · `mfa_required` · `state` · `created_by`.
**Invariants.** I1 Local accounts always require MFA (ADM-142). I2 A `directory` account is
disabled, and its sessions revoked, when sync observes the AD user disabled or deleted, or out of
every scope the account was admitted through. Sign-in also refuses it when `accountExpires` is in
the past, checked at every sign-in, because expiry involves no directory write
([accountExpires](https://learn.microsoft.com/en-us/windows/win32/adschema/a-accountexpires)). I3 There
are no default credentials: the first account is created with a one-time bootstrap secret at
install (ADM-145). I4 A tenant always has at least one active account holding `tenant-owner`, so
the last one cannot be removed.
**Lifecycle.** `invited → active ⇄ disabled → deleted`. Audit keeps the ID and a name snapshot.

### DM-31 Session · T · owner `platform/authn`
**Definition.** An authenticated console session, kept in PostgreSQL so any node serves it.
**Key attributes:** `id_hash` · `account_id` · `methods` · `mfa_at` · `idle_expiry` ·
`absolute_expiry` · `client_ip`.
**Invariants.** I1 It respects the concurrent-session limit (ADM-145). I2 It is revoked when its
account is disabled.
**Lifecycle.** `active → expired | revoked`.

### DM-32 ApiToken · T · owner `platform/authn`
**Definition.** A credential that lets a script act as its owning account. **Replaces (ME):**
technician authtokens (ADM-141).
**Key attributes:** `owner_account_id` · `name` · `secret_hash` · `permission_subset` ·
`scope_narrowing` · `expires_at` (mandatory) · `last_used`.
**Invariants.** I1 Effective authority is the owner's current authority intersected with the
token's subset. A disabled owner makes the token dead. I2 The secret is shown once.
**Lifecycle.** `active → expired | revoked`.

### DM-33 Permission · R · declared by each module (EP-6)
**Definition.** A named capability that an operation or Action requires, such as
`objects.user.create`, `helpdesk.password.reset` or `secret.read:laps`. **Replaces (ME):**
task-level privileges (ADM-125).
**Key attributes:** `id` · `kind` (action, read, admin, secret) · `attribute_constrainable` ·
`risk`.
**Invariants.** I1 Every OpenAPI operation declares exactly one (`x-permission`). I2 Secret
values are reachable only through `secret.*` permissions (safe-primitives §3.7).
**Lifecycle.** `active → deprecated → removed` (X6).

### DM-34 Role · T · owner `platform/authz`
**Definition.** A named set of privileges. A privilege is a Permission plus a mode and
constraints. **Replaces (ME):** help-desk roles (ADM-125), built-in roles (ADM-126), requester
roles (ADM-117), technician templates (ADM-132), report restrictions (ADM-102) and the LAPS
role (ADM-060).
**Key attributes:** `name` · `built_in` · `privileges[]`: `permission`, `mode` (`execute` or
`request`), and constraints: attribute allowlist, template allowlist, report categories,
`max_batch` (1 means no bulk), `csv_allowed`.
**Invariants.** I1 Built-in roles ship as data and are read-only; clone one to change it.
`tenant-owner` holds every permission. I2 `request` mode means the Operation must pass the
workflow gate (DM-64).
**Lifecycle.** `active → archived`. A role can be archived only with no assignments, or through an
Operation that revokes them.

### DM-35 DelegationScope · T · owner `modules/delegation`
**Definition.** The set of directory objects a grant reaches. **Replaces (ME):** OU-based
(ADM-127), include/exclude group (ADM-129) and cross-domain (ADM-130) delegation.
**Key attributes:** `entries[]`: connection, `root_kind` (`naming_context`, `ou_subtree`,
`ou_one_level`, `group_members`), `root_guid`, include or exclude, `entry_state` (`active`,
`root_deleted`) · target filters (object kinds,
`groups_include`, `groups_exclude`).
**Invariants.** I1 Roots are GUIDs. A moved root keeps its scope. A deleted root grants nothing and
never widens to the domain (safe-primitives LF-31). A root restored from the Recycle Bin keeps its
GUID, so its scope would silently return. Instead the entry stays inactive until an audited
Operation reactivates it. I2 It is evaluated against inventory ancestry,
and re-checked against the live parent chain at Plan (blueprint §11). I3 Exclusion beats
inclusion. I4 Counts and pages are computed after scope trimming (LF-39). I5 `tier0` objects are
outside every write scope in v1 (ADR-0002 rule 9; FD-11).
**Lifecycle.** `active → archived` (only when unassigned).

### DM-36 RoleAssignment · T · owner `platform/authz`
**Definition.** It grants a subject a Role over a DelegationScope. **Replaces (ME):** the
technician↔role↔domain/OU mapping (ADM-125…130) and group-based delegation (ADM-128).
**Key attributes:** `subject` (account, directory group as connection+GUID, or automation policy) ·
`role_id` · `scope_id` (null for roles with no directory reach) · `valid_from` / `valid_until` ·
`granted_by` · `state`.
**Invariants.** I1 **No escalation.** The grantor must hold every privilege of the role over the
whole scope, or be `tenant-owner`. This is the class of CVE-2024-24409
([advisory](https://www.manageengine.com/products/ad-manager/admanager-kb/cve-2024-24409.html)).
I2 A group subject's membership is **directory** membership, resolved transitively from inventory
including primary-group edges. It is not token membership: it is broader than `tokenGroups`, which
leaves out other domains' domain-local groups
([tokenGroups](https://learn.microsoft.com/en-us/windows/win32/adschema/a-tokengroups)).
Deactivated links never count. Subject groups must be security groups; a distribution group grants
nothing. An FSP member grants only if its SID resolves to an Account in a connected forest.
`sIDHistory` is not followed. Members lose rights when they leave the group or are disabled, within
sync freshness (ADM-128). I3 Effective authority is the union of assignments, and each privilege applies only
within its own assignment's scope. Role A's permission is never combined with scope B.
**Lifecycle.** `scheduled → active → expired | revoked`.

### DM-37 AuthenticatorEnrollment · T · owner `platform/authn` (EP-10)
**Definition.** A factor enrolled by an account (console MFA) or by an end user (FD-05 TOTP).
**Replaces (ME):** console 2FA enrollment (ADM-142). It is also the v1 slice of ADSSP enrollment.
**Key attributes:** `subject` (account, or directory user as connection+GUID) · `method` (totp,
webauthn, email_otp, sms_otp) · `sealed_secret` or `public_credential` · `label` · `last_used` · `state`.
**Invariants.** I1 Seeds are sealed and never returned after enrollment. I2 Zero-touch factors
(email or mobile already in AD or HR) are read live and are not enrollments.
**Lifecycle.** `pending → active → revoked`.

### DM-38 CallerVerification · T · owner `modules/helpdesk` (ENH-09)
**Definition.** One challenge a technician issues to prove a caller is the target user before a
reset or unlock. **Replaces (ME):** none. It extends the reset console (ADM-136); caller
verification is ENH-09 (scope lock §3.5).
**Key attributes:** `technician_account_id` · `target` (connection+GUID) · `factor` ·
`destination_masked` · `code_hash` · `expires_at` · `attempts` · `operation_id` · `state`.
**Invariants.** I1 The destination comes only from data held before the call (AD or HR), never
from what the technician types. I2 The code is never stored in clear or logged. I3 A verified
challenge authorises Actions only on its target, once, within its window. I4 The factor is
recorded in the same audit event as the reset.
**Lifecycle.** `issued → verified | failed | expired | cancelled`.

## 4. Change: operations and jobs

### DM-40 Action · R · declared by modules (EP-3)
**Definition.** A typed write with `Plan`, `Apply`, `Verify` and `Inverse` (blueprint §4.2), for
example `objects.user.create` or `m365.licence.assign`. **Replaces (ME):** management tasks and
automatable tasks (ADM-107), orchestration blocks (ADM-045, ADM-109) and report actions
(ADM-098).
**Key attributes:** `id` · `permission` · `input_schema` · `reversibility` (reversible, lossy,
irreversible) · `providers` (ad, entra) · `capabilities`.
**Invariants.** I1 It is the only path to a directory write (X9). I2 `Plan` has no side effects.
I3 It declares `Inverse` or `Irreversible`. I4 No Action runs a free-form script. ME's custom
scripts (ADM-019, ADM-112) have no equivalent.
**Lifecycle.** `active → deprecated → removed` (X6). Templates, policies, workflows and report
definitions that reference it are migrated first.

### DM-41 Operation · T · owner `platform/operation` (guarantees: T-0047)
**Definition.** One intent to change directories, planned before it runs: a single edit, a
50,000-row CSV, a workflow request's execution, an automation run's step, act-on-results, or an
undo. **Replaces (ME):** bulk jobs, CSV imports and the execution side of workflow (ADM-010, 011,
034, 116).
**Key attributes:** `origin` (console, api, csv, workflow, automation, report_results, undo,
migration) · `initiator` chain (account, API token, automation policy, approvals) · `actions[]` ·
`input` (typed; secrets excluded) · `template_version` · plan summary (counts, reversibility,
approvals needed) · `plan_valid_until` · `undo_of` · `request_id` · `state`.
**Invariants.** I1 A plan always comes before apply. Authorization is checked at plan time and
re-checked per item at apply, against live ancestry. I2 Partial success is never reported as
success. I3 Undo is a new Operation, with `undo_of` set, through the same gate. I4 A plan older
than `plan_valid_until` must be re-planned before it is approved or applied.
**Lifecycle.**
`draft → planning → planned → awaiting_approval → approved | rejected`, then
`approved → queued → running → succeeded | partially_succeeded | failed | cancelled`.
`planned` can also go to `expired`. Without a gate, `planned → queued`. T-0047 ratifies the
transitions and may rename them, and this file then follows in the same change.

### DM-42 OperationItem · T · owner `platform/operation`
**Definition.** One target, or one CSV row, of an Operation, with its ordered steps. Each step is
one Action applied to that target.
**Key attributes:** `item_no` · `target` (GUID, or "to be created" with a planned display DN) ·
`input_row` · `planned_diff` (attribute: before → after) · `steps[]` (`action_id`, `dc`,
`state`, `outcome`, `read_back`, `inverse_input`, `reversibility`) · `state`.
**Invariants.** I1 The idempotency key is `(operation, item, step)`. I2 The before-state captured
at plan is re-checked at apply. If it changed, the item fails `stale_state` and is never
overwritten. I3 Verify reads back from the DC that applied. I4 Inverse inputs contain no secrets,
and irreversible steps are flagged at plan.
**Lifecycle.** `pending → planned | skipped | blocked`, then `planned → applying → applied →
verified | verify_failed`, or `applying → failed`. `verified → undone` once an undo is verified.

### DM-43 Job · execution record in River (global, registered) · owner `platform/jobs`
**Definition.** A unit of background execution that advances a domain record: an operation chunk,
a report run, a sync pass or a delivery. **Replaces (ME):** the scheduler's internal tasks.
**Key attributes:** `kind` (EP-5) · `args` (`tenant_id` + a typed reference to the domain record) ·
`unique_key` · `attempt` · `scheduled_at`.
**Invariants.** I1 A job is never the system of record. The OperationItem, ReportRun or
SyncCursor holds the truth, and a lost job is re-derived from it. I2 Args carry `tenant_id`, and
the wrapper opens `WithTenantTx` first. Platform jobs are registered. I3 Only `platform/jobs`
imports River (ADR-0002 T5).
**Lifecycle.** River's states: `scheduled | pending | available → running → completed`, or
`running → retryable → … → discarded`, or `→ cancelled`
([JobState](https://pkg.go.dev/github.com/riverqueue/river/rivertype#JobState)).

### DM-44 Schedule · T · owner `platform/jobs`
**Definition.** A recurrence owned by one entity: an automation policy, a report schedule or a
cleanup policy. One shape serves all of them.
**Key attributes:** `recurrence` (hourly, daily, weekly, monthly, custom) · `time_zone` (IANA) ·
`window` · `next_run_at` · `owner_ref` · `state`.
**Invariants.** I1 The recurrence is evaluated in its time zone, and `next_run_at` is stored in
UTC. A local time skipped by DST runs at the next valid instant; a repeated one runs once.
I2 Misfires after downtime run once, never as a burst.
**Lifecycle.** `active ⇄ paused → deleted` (with its owner). **Replaces (ME):** scheduler options
(ADM-101, ADM-104).

## 6. Automation and workflow

### DM-60 AutomationPolicy · T · owner `modules/lifecycle`
**Definition.** A versioned rule that selects objects and runs ordered Action steps on them, with
delays, on a trigger. **Replaces (ME):**
- scheduled automation (ADM-104), automation policies (ADM-105), controlled automation (ADM-106);
- the disable and delete policies (ADM-043, ADM-044) and the cleanup policy (ADM-147);
- HR, CSV and database provisioning (ADM-039, 040, 041), movers (ADM-042);
- expiry reminders (ADM-047), the offboarding blocks (ADM-045).

**Key attributes:** `owner_account_id` · `trigger` (`schedule` DM-44; `directory_state`, for
example "user became disabled", observed by sync whoever made the change; `operation_event`, an
activeDIQ Action that succeeded; `data_source` DM-63) · `selector` (report definition +
parameters, data-source rows, or the triggering object) · `steps[]` (Action ID, parameters, delay

**Invariants.** I1 Every run produces Operations (X9). Automation is never a side door. I2 It acts
as itself: the policy is a RoleAssignment subject (DM-36), so its reach is explicit, and DM-36.I1
stops it from exceeding its grantor's reach. I3 If a run plans more than `max_objects` items, it
holds for approval instead of applying (blast-radius guard). I4 While in `shadow`, it plans and
compares but never applies.
**Lifecycle.** `draft → shadow → active ⇄ paused → archived` (`shadow` is optional). It is flagged
`orphaned` when its owner is no longer active. It keeps running, and tenant owners are notified.

### DM-61 PolicyProgress · T · owner `modules/lifecycle`

`last_operation_id` · `state`.
**Invariants.** I1 One row per (policy, object). I2 A due step runs only if the object still
matches the selector when it is planned, so a re-enabled user leaves the track and is never
deleted.
**Lifecycle.** `active → completed | exited | failed`.

### DM-62 AutomationRun · T · owner `modules/lifecycle`

**Key attributes:** `policy_id` + `version` · `fired_at` · `selected_count` · `operation_ids[]` · `state`.

### DM-63 DataSource · T · owner `modules/lifecycle`

## 7. Reporting

### DM-70 Dataset · R · declared by `directory/inventory`, `platform/audit` (EP-8)
**Definition.** A typed, queryable view that reports may target, such as `inventory.users` or
`audit.events`.
**Key attributes:** `id` · `columns` (typed, pre-quoted identifiers) · `scope_column` (GUID
ancestry) · `freshness_source`.
**Invariants.** I1 `store/reportsql` is the only dynamic SQL, and it uses only registry
identifiers. I2 It never exposes a registered-global table (ADR-0002 T5).
**Lifecycle.** `active → deprecated → removed` (X6).

### DM-71 ReportDefinition · T (plus shipped definitions) · owner `modules/reports`
**Definition.** A report as data: an AST over one Dataset. **Replaces (ME):** prebuilt reports
(ADM-083…093), the custom report builder (ADM-097), scope and filters (ADM-099) and compliance
sets (ADM-093).
**Key attributes:** `origin` (shipped, custom, imported via the crosswalk MIG-05) · `version` ·
`dataset` · `ast` (columns, filters, sort, grouping) · `parameters` · `category` ·
`compliance_tags` · `owner` · `shared_with` · `attached_actions` (Action IDs, ADM-098).
**Invariants.** I1 Results are always trimmed to the **runner's** authority. Sharing a definition
never shares data (LF-39). I2 Shipped definitions are immutable; clone one to customise it. I3 An
admin LDAP filter (ADM-097) is parsed by P1 into an AST, never stored as text that is executed.
How it maps onto inventory datasets is `[OPEN → report builder spec]`.
**Lifecycle.** `draft → published → archived`. Shipped definitions go `active → deprecated`.

### DM-72 ReportRun · T · owner `modules/reports`
**Definition.** One execution of a definition version with parameters. **Replaces (ME):** report
generation and export (ADM-100).
**Key attributes:** `definition_version` · `parameters` · `runner` · `scope_applied` · `as_of`
(freshness watermark) · `row_count` · `result_blob` · `exports[]` (format, blob, expiry) · `state`.
**Invariants.** I1 Freshness is stated, never "live" when it is not. I2 Exports go through the
output encoders (T-0029). I3 Blobs are tenant-prefixed and expire.
**Lifecycle.** `queued → running → succeeded | failed | cancelled`, then `succeeded → expired`.

### DM-73 ReportSchedule · T · owner `modules/reports`
**Definition.** A recurring run plus delivery. **Replaces (ME):** scheduled reports (ADM-101) and,
through migration, imported schedules (MIG-06).
**Key attributes:** `definition_id` · `parameters` · `schedule` (DM-44) · `owner_account_id` ·
`delivery` (accounts or external addresses, formats, attachment or link, notify only if data) ·
`execution_owner` (MIG-14) · `state`.
**Invariants.** I1 Each run uses the owner's authority at that moment. If the owner is disabled,
the schedule pauses. I2 Delivery to an external address requires its own permission.
**Lifecycle.** `active ⇄ paused → archived` (plus `shadow` while ME still runs it).

## 8. Evidence and integration

### DM-80 AuditEvent · T · append-only · owner `platform/audit` (guarantees: T-0047)
**Definition.** One entry in activeDIQ's own audit trail. Each tenant has one hash chain.
**Replaces (ME):** the help-desk audit (ADM-137), admin audit (ADM-138), technician logons
(ADM-139) and automation audit history (ADM-114).
**Key attributes:** `seq` (per tenant, gapless) · `at` · `kind` (registry, EP-7) · `actor` chain
(principal, plus the API token, automation policy and approvals it acted through) · `targets`
(connection+GUID with a display snapshot) · `operation`/`item`/`request` refs · `outcome` ·
`details` (typed per kind) · `verification_factor` (ENH-09) · `client_ip` · `prev_hash` · `hash`.
**Invariants.** I1 One chain per tenant. Events are appended serially and `seq` has no gaps.
I2 Immutable (X5). Retention deletes only below a checkpoint (DM-81). I3 Every operation step,
sign-in, RBAC change, settings change, secret read, presence grant, enrollment and credential
change emits an event. I4 Details never carry a `Secret`. Targets keep the DN as it was at the
time, because DNs change.
**Lifecycle.** `appended → checkpointed → archived` (exported and still verifiable) `→ purged`.

### DM-81 ChainCheckpoint · T · append-only · owner `platform/audit`
**Definition.** A signed statement of the chain head at a given `seq`.
**Key attributes:** `seq` · `hash` · `signed_at` · `signature` · `key_id`.
**Invariants.** I1 Checkpoints are kept for the tenant's life, so verification starts from any
retained checkpoint after events are purged.
**Lifecycle.** `recorded` (terminal).

### DM-82 NotificationChannel · T · owner `platform/notify` (EP-9)
**Definition.** A configured way out: SMTP or a mail API, an SMS gateway, or a SIEM (syslog, CEF,
HTTP). **Replaces (ME):** mail, SMS and proxy settings (ADM-205) and SIEM forwarding (ADM-198).
**Key attributes:** `kind` · `settings` · `sealed_credentials` · `last_test` · `state`.
**Invariants.** I1 Credentials are sealed and never returned. The egress proxy is a platform
setting.
**Lifecycle.** `draft → active ⇄ disabled → archived`.

### DM-83 NotificationTemplate · T (shipped defaults + overrides) · owner `platform/notify`
**Definition.** The message for a purpose and channel kind. **Replaces (ME):** notification
templates and profiles (ADM-204).
**Key attributes:** `purpose` · `channel_kind` · `locale` · `subject` · `body` with typed
placeholders.
**Invariants.** I1 Placeholders come from the purpose's typed variable set and are rendered
through the output encoders. No placeholder resolves to a `Secret` (§11 Q4).
**Lifecycle.** `active → archived`.

### DM-84 Delivery · T · owner `platform/notify`
**Definition.** One attempt to deliver one message to one recipient. **Replaces (ME):**
notification history (ADM-204).
**Key attributes:** `channel_id` · `template_version` · `recipient` · `source_ref` (operation,
report run, request, reminder) · `attempts` · `provider_message_id` · `state`.
**Invariants.** I1 It stores metadata and variable references, not rendered bodies.
**Lifecycle.** `queued → sent`, or `queued → failed → (retry) → sent | given_up`.

### DM-85 ItsmConnection · T · owner `modules/itsm`
**Definition.** A link to a service-desk system. One adapter shape covers every system.
**Replaces (ME):** the ServiceNow and ServiceDesk Plus integrations (ADM-191, ADM-192).
**Key attributes:** `kind` (servicenow, servicedesk_plus) · `endpoint` · `sealed_credentials` ·
`field_mapping` · `modes` (inbound requests, status write-back) · `state`.
**Invariants.** I1 An inbound ticket creates a Request (DM-65), never a direct write.
**Lifecycle.** `draft → active ⇄ disabled → archived`.

## 12. Review log

- 2026-10-02 · ad-expert · AD and Entra semantics review of X3, DM-10…DM-22, DM-30.I2, DM-35,
  DM-36.I2 and the §9 map. The review is based on documentation only, with no lab run. Claims that
  need a Windows lab are tagged `[LAB: Windows]` (cross-domain move, LVR metadata, Recycle Bin
  restore, lockout timing). There were 13 findings: 11 fixes and 2 confirmations with additions.
  **All 13 were applied.**

| # | Finding | Disposition |
| --- | --- | --- |
| F1 | Forest identity is the forest root domain NC's objectGUID, read from the root crossRef `nCName`, with the root domain SID as a second check. DNS and NetBIOS names are snapshots, because a rename keeps the GUID | Applied: DM-10 key attributes; §9 row |
| F2 | Re-promotion creates a new NTDS Settings object, so a new `dsa_guid`. `invocationId` also changes with the VM-GenerationID. USN cursors key on `(dsa_guid, invocation_id)` | Applied: DM-15 attributes, I4, I5 |
| F3 | Recycled objects are never undeletable. Tombstone reanimation keeps the GUID, SID, sIDHistory and searchFlags-0x8 attributes and loses all link values. A restore needs a live parent. Objects deleted before the Recycle Bin was enabled are not restorable through it. A cross-domain move expunges the object and leaves an `infrastructureUpdate` proxy, so a known GUID appearing in another NC is a move, and resync is forest-wide by GUID | Applied: DM-16 AD lifecycle, DM-16.I1, DM-19.I3 |
| F4 | Entra restorable types: users, M365 groups, cloud security groups (preview), applications, service principals and administrative units. Distribution groups are not restorable. Synced objects are restored in AD. Delta `@removed.reason` maps to soft-deleted or purged | Applied: DM-16 Entra lifecycle; closes Q3. Restoring a synced group from Entra stays `[UNVERIFIED]` |
| F5 | OK on DM-17. FSPs also stand for well-known SIDs, and a same-forest member from another domain is not an FSP. With the Recycle Bin off, links are removed, not deactivated | Applied: DM-17.I4 and lifecycle |
| F6 | OK on DM-18. DirSync returns final state only. `origin` is nullable for pre-LVR values, and the originating time is the originating DC's clock | Applied: DM-18 attributes, I2, I2a |
| F7 | A DirSync cookie is reused only on its issuing DC; anything else ends in a full sync. Children of a moved parent are not reported. Graph delta tokens expire after 7 days, and 410 means a full sync. Reader controls go to T-0018 | Applied: DM-19 `issuing_dsa_guid`, I4–I6; control details referenced to T-0018 |
| F8 | Anchor encoding: only non-string anchors are base64. Connect and Cloud Sync differ in their anchor choice. Groups match on `onPremisesSecurityIdentifier`. After a migration, match ms-DS-ConsistencyGuid first. `isCloudManaged` (beta) flips the source of authority | Applied: DM-20 attributes, I1, I1a, I1b, lifecycle |
| F9 | Group delegation uses directory membership, not token membership. Deactivated links never count. Only security groups grant. An FSP grants only if it resolves to an Account. sIDHistory is not followed | Applied: DM-36.I2 |
| F10 | `tombstoneLifetime` absent means 60 days, and `msDS-deletedObjectLifetime` absent follows it. Both, and the Recycle Bin flag, are forest-wide | Applied: moved from DM-14 to DM-10.I6 |
