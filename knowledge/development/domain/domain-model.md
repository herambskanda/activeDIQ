# activeDIQ domain model v0

The shared vocabulary every feature lands on. Each entity has an ID (`DM-nn`) and numbered
invariants (`DM-nn.In`) so specs, tickets and tests can cite them ("violates DM-16.I2").
It restates and does not override [ADR-0002](../decisions/0002-deployment-model.md) (tenancy) or the
[blueprint](../architecture/blueprint.md) (components). Where they disagree, the ADR wins and this
file is the bug. Table shapes, indexes and partitioning are decided by the owning build tickets
and T-0026. This file fixes **what exists, what is always true, and how it moves**.

**Kinds.** `P` platform scope: a registered-global table (ADR-0002 rule 4), set by the
installation operator. `T` tenant scope: `tenant_id` plus forced RLS, set only through the public
API. `D` directory-observed: tenant scope, written only by `sync` or by an Action's verified
outcome, and read-only to everything else. `R` registry: declared in code through the
`Registrar` (blueprint §4.1). It is not a table, but persisted data references it by ID.
**Owner** is the package that owns the entity's tables (blueprint §2 rule 6). Its owner key is the
top-level package under `internal/platform`, `internal/directory`, `internal/connector` or
`internal/modules` that the migration filename names ([ADR-0003](../decisions/0003-module-system-extension-points-only-on-ramp.md) rule 6).
ADR-0003 rule 9 checked every owner line below against those rules.
**`[LAB: Windows]`** marks AD behaviour that Microsoft documents (cited inline) but that we have
not yet reproduced against a Windows DC. Code must not rely on such a claim until a lab test has
confirmed it (T-0051, §11 Q8).

## 0. Invariants for every entity

- **X1 Tenancy.** Every `T`/`D` row has `tenant_id`. It leads the PK and every unique index, and
  every FK to a tenant table is composite (ADR-0002 "Where tenancy lives"). No entity references
  another tenant's row. `P` rows never reference a `T` row.
- **X2 Surrogate IDs.** These are UUIDs generated by the application. Row IDs are time-ordered
  (v7), and tenant IDs are random (v4, ADR-0002 rule 5). Directory identities are the directory's
  own GUIDs (X3), never surrogates.
- **X3 Directory identity.** A directory object is `(connection_id, object_guid)`: the AD
  `objectGUID` or the Entra object `id`. A DN, SID, sAMAccountName or UPN is never a key, FK or
  join column. DNs change on rename and move, and SIDs change on a cross-domain move
  ([objectGUID](https://learn.microsoft.com/en-us/windows/win32/adschema/a-objectguid),
  [sIDHistory](https://learn.microsoft.com/en-us/windows/win32/adschema/a-sidhistory)). Every
  reference column holds a GUID. Display strings (DN, name) are stored as *snapshots* beside it.
- **X4 Secrets never persist in clear.** Passwords, OTP codes, LAPS/BitLocker values and
  `SecretAttrs` (safe-primitives §3.7) are never stored in clear. Credentials and seeds are stored
  *sealed* under the tenant data key. A secret input of an in-flight operation step (a password
  being set) is stored sealed only while that step needs it, and is deleted at the step's terminal
  state or within 72 hours (ADR-0005 rule 9). No `Secret` is ever serialised into an
  entity, an audit detail, a notification or an export.
- **X5 Append-only records** (ChangeRecord, AuditEvent, ApprovalDecision, ChainCheckpoint) are
  never updated. Only retention deletes them, and only as an explicit, audited path. Their
  lifecycle states are **derived and never stored**: these tables have no state column, so no
  state change can ever be an UPDATE (fitness check T-0050). Each entity says what its states
  are derived from.
- **X6 Registry IDs are stable strings, never reused.** A persisted reference to a registry entry
  (Permission, Action, Dataset, audit kind, job kind) blocks that entry's removal until a
  migration rewrites the reference.
- **X7 Definitions are versioned; runs pin versions.** Templates, naming formats, workflow
  definitions, automation policies and report definitions publish immutable versions. Every
  Operation, Request, AutomationRun and ReportRun records the version it used.
- **X8 Time** is `timestamptz` in UTC. A schedule's time zone is data (DM-44). FILETIME values are
  converted at the codec (P3).
- **X9 Every directory write is an Operation** (DM-41) executing a registered Action (DM-40). No
  entity offers a side door: templates, automations, workflows, report results and ITSM tickets
  all *produce* Operations.
- **X10 Our records outlive the directory's.** Deleting an object, connection or account never
  deletes our audit trail. Retention is a tenant setting per record class (ADM-206).
- **X11 Personal data is erasable without touching the evidence.** Personal display values inside
  append-only records (name, DN and UPN snapshots, mail, phone, the old and new values of personal
  attributes, free-text comments) must be erasable **without updating or deleting the record and
  without breaking chain verification** (X5, DM-80.I1). Two mechanisms meet this. In the first, the
  record holds only a pseudonymous form (the GUID, plus a keyed MAC of the value for search), and
  the clear value lives in a per-subject side record that erasure deletes. In the second, the
  value is sealed under a per-subject key that erasure destroys (crypto-shredding), and the hash
  covers the sealed form. **ADR-0005 rule 12 chose the first**, with a salted commitment
  (`PersonalRef`) in the record and the clear value in `platform/personal`; erasure deletes the
  subject's salt and values (§11 Q9, closed). Either way, it must be in place **before
  the first audit event is written**: a chain whose hash covers clear names cannot be made
  erasable later. After erasure, the event, its GUIDs and its hash remain, and the UI shows
  `[erased]`. The erasure is itself audited, without the erased values. This is the mechanism
  behind ME's "anonymize data on deletion" (ADM-207). X10 still holds, because no event is
  deleted. Mutable records (Operation input, Request, Account) are erased in place.

**Lifecycle notation.** `a → b` is a transition. `a ⇄ b` is reversible. A *state* is persisted,
except on the append-only entities (X5: DM-18, DM-66, DM-80, DM-81), whose states are derived
from other records and never stored. *Health* (reachable, degraded, lagging) is observed, shown,
and never a lifecycle state.

## 1. Platform and tenancy

### DM-01 Tenant · P · owner `platform/tenant`
**Definition.** The isolation boundary for all customer data. A self-hosted install has exactly
one; a SaaS cell has many. **Replaces (ME):** none (ADMP is single-organisation).
**Key attributes:** `id` (random UUID) · `parent_tenant_id` (null in v1) · `name` · `state` ·
`placement` (cell, database; SaaS only) · `region` · `created_at` · `state_changed_at`.
**Invariants.** I1 A self-hosted install has exactly one tenant, created by the installer. There
is no default-tenant constant (ADR-0002 rule 5). I2 `tenant.ID` is minted only by authn, the job
wrapper, registered platform paths and tests. It comes from an authenticated principal, never from
request content. I3 `parent_tenant_id` references an existing tenant and the graph is acyclic.
RLS never admits a parent into a child's rows; MSP work iterates tenants under a grant (E5.6).
I4 Each tenant has exactly one audit hash chain (DM-80) and one active data key (DM-02).
I5 Deletion shreds the tenant's keys before rows are purged. Only the `id` and timestamps survive,
in the `deleted` row.
**Lifecycle.** `provisioning → active ⇄ suspended → deleting → deleted`. Self-hosted tenants are
created `active`, because the `tenant-provisioning` capability is not composed there. While
`suspended`: sign-in is refused, jobs are paused and connectors are refused; data is kept. The
export window during `deleting` is `[OPEN → E5.6]`.

### DM-02 TenantKey · T · owner `platform/keys`
**Definition.** A tenant's data-encryption key, wrapped by the installation KEK from the profile's
key provider. Everything sealed (DM-11, DM-37, DM-63, DM-82, DM-85) is sealed under it.
**Key attributes:** `version` · `wrapped_dek` · `kek_ref` (provider, key id) · `state` · `created_at`.
**Invariants.** I1 Exactly one `active` version per tenant. I2 Every sealed value records the key
version that sealed it. I3 The plaintext DEK exists only in memory. I4 Shredding destroys every
version. The rotation procedure is `[OPEN → T-0007]`.
**Lifecycle.** `active → retired` (decrypt-only) `→ shredded`.

### DM-03 Node · P · owner `platform/update` (registry of server processes)
**Definition.** One running `server` process of the installation. Nodes are stateless, and HA is
achieved by adding them (ADR-0002 rule 6). **Replaces (ME):** primary/standby HA and load-balancer
nodes (ADM-210).
**Key attributes:** `id` · `hostname` · `version` · `roles` · `started_at` · `last_heartbeat`.
**Invariants.** I1 A node holds no state that another node needs. I2 A node whose heartbeat has
expired loses its leases (DM-06). I3 Only a node running the current Release's version may take
the migration lease.
**Lifecycle.** `joining → active → draining → gone`.

### DM-04 HostnameBinding · P · owner `platform/apihost`
**Definition.** It maps a public hostname to a tenant for **anonymous end-user flows**: in v1 the
TOTP enrollment page (FD-05), and SSPR from M4.
**Key attributes:** `hostname` (lower-case, IDNA) · `tenant_id` · `capabilities` (closed set of
anonymous flows) · `state`.
**Invariants.** I1 One hostname maps to one tenant. I2 It grants only anonymous-flow
capabilities, never console or API access (ADR-0002 Request row).
**Lifecycle.** `active ⇄ disabled → deleted`.

### DM-05 Release · P · owner `platform/update`
**Definition.** A signed release manifest that the installation has seen, with its apply history
(ENH-07). **Replaces (ME):** service packs and automatic hotfixes (ADM-209, ADM-213).
**Key attributes:** `version` · `manifest_digest` · `signing_key_id` · `courier` (online,
offline) · `state` · `applied_at` · `rollback_reason`.
**Invariants.** I1 Only a verified release can be staged. Both couriers use one verifier
(ADR-0002 rule 7). I2 At most one release is `applying`, under the migration lease. I3 Migrations
are expand-only. I4 Rows are never deleted.
**Lifecycle.** `discovered → verified | rejected`, then `verified → staged → applying → applied |
rolled_back`.

### DM-06 Lease · P (platform work) and T (tenant work) · owner `platform/jobs`
**Definition.** Exclusive, expiring ownership of singleton work: the sync reader per partition,
schedulers and migrations. One shape, two tables: platform leases are global, tenant leases are
under RLS.
**Key attributes:** `resource_key` · `holder_node` · `fencing_token` (monotonic) · `expires_at`.
**Invariants.** I1 At most one holder. I2 Writes made under a lease carry its fencing token. For
example, a SyncCursor write is refused if the token is stale.
**Lifecycle.** `free → held → (renewed) → released | expired`.

## 2. Directories

### DM-10 Connection · T · owner `directory/connection` (model in `directory/model`; written by the `connections` module through `connection`'s Go API, ADR-0003 F1)
**Definition.** One directory activeDIQ manages: an **AD forest** or an **Entra tenant**. Each
connection has its own credential, bindings and sync. **Replaces (ME):** the "domain" in Domain
Settings (ADM-212; per-domain settings move to DM-14) and the M365 tenant configuration (ADM-159).
**Key attributes:** `kind` (`ad_forest`, `entra_tenant`) · `display_name` · `directory_identity`
(AD: the objectGUID of the forest root domain NC, read from the root domain's crossRef `nCName`
as an extended DN, with the forest root domain SID as a second check; Entra: the tenant ID) ·
`forest_dns_name` and `forest_netbios_name` (snapshots: a domain rename keeps the GUID,
[domain rename](https://learn.microsoft.com/en-us/previous-versions/windows/it-pro/windows-server-2008-R2-and-2008/cc816795(v=ws.10))) ·
forest-wide deletion settings (AD only): `recycle_bin_enabled`, `tombstone_lifetime_days`,
`deleted_object_lifetime_days` · `verified_at` · `transport_security` (LDAPS or StartTLS) ·
`dc_affinity` (site priority, per-OU preferred DCs, ADM-133) · `sync_attribute_set` (additions to
the default set) · `credential_id` · `state` · takeover attestation (Entra only, I7):
`attested_by`, `attested_at`, `attested_values`, `attestation_max_age`, `first_attested_at`
(set once, I7(f)); `takeover_protection` is derived from these and never stored.
**Invariants.** I1 `directory_identity` is fixed at first verification. A connection cannot be
re-pointed at another forest or tenant, because that would mix two directories' GUID spaces.
I2 `(kind, directory_identity)` is unique per tenant. I3 An `active` connection has at least one
binding (DM-13). I4 The security floor is not configurable downward: TLS, signing, sealing and
channel binding are always on (ADR-0002 rule 8). I5 Removal never deletes audit events (X10).
Inventory is purged by retention. I6 The deletion settings are read from the directory and never
assumed. They are forest-wide, so they live here and not on NamingContext. An absent
`tombstoneLifetime` means 60 days; 180 is written only when the forest was created on WS2003 SP1
or later ([tombstoneLifetime](https://learn.microsoft.com/en-us/windows/win32/adschema/a-tombstonelifetime)).
An absent `msDS-deletedObjectLifetime` means it equals the effective tombstone lifetime
([ADAC L200](https://learn.microsoft.com/en-us/windows-server/identity/ad-ds/get-started/adac/advanced-ad-ds-management-using-active-directory-administrative-center--level-200-)).
I7 **Takeover-protection attestation (Entra only).** DM-20.I4(f) depends on two tenant sync
features: `blockCloudObjectTakeoverThroughHardMatchEnabled` and `blockSoftMatchEnabled`. Graph
lets only a signed-in Global Administrator read them, through a delegated permission. Neither
v1.0 nor beta offers an application permission
([get onPremisesDirectorySynchronization](https://learn.microsoft.com/en-us/graph/api/onpremisesdirectorysynchronization-get?view=graph-rest-1.0)).
The connector is app-only and holds no admin role (ADR-0002 rule 7), so activeDIQ never reads the
flags itself. They are an **attested tenant fact**:
- (a) **Attest.** An account holding `connections.takeover.attest` over this connection's
  `entra_tenant` scope starts the attestation, with step-up (threat model §7.4). A Global Administrator of the same tenant then signs
  in through a delegated, read-only flow (`OnPremDirectorySynchronization.Read.All`, no
  `offline_access`). The server performs the one read itself and rejects a token whose `tid` is
  not `directory_identity`. It records the result and discards the token. No token is stored, and
  the values are read from Graph, never typed in.
- (b) **Record.** Each attestation is an audit event (DM-80). It records who started it, which
  Global Administrator signed in (object ID, with the display snapshot handled under X11), when,
  and both values. The connection keeps the latest attestation in `attested_by`, `attested_at` and
  `attested_values`.
- (c) **State.** `takeover_protection` is computed from the stored inputs at every evaluation, so
  ageing out needs no job. It is `attested` only while all three hold:
  - both values were `true`;
  - `attested_at` is younger than `attestation_max_age` (default 90 days; a tenant can shorten
    it but never lengthen it);
  - no demotion signal (d) has arrived since.

  Otherwise it is `unattested` (never attested), `open` (a value was `false`) or `stale` (aged out
  or demoted). Any state except `attested` makes every correlation in the tenant `candidate`
  (`tenant_takeover_open`). Connection health shows the state and the fix, and warns 14 days
  before an attestation ages out.
- (d) **Demotion signal.** A change to the tenant's sync features, recorded in the Entra directory
  audit log after `attested_at`, makes the state `stale` until a new attestation is made. The log
  is read app-only with `AuditLog.Read.All`
  ([directoryAudits](https://learn.microsoft.com/en-us/graph/api/directoryaudit-list?view=graph-rest-1.0)).
  The audit activity name is `[UNVERIFIED]` (T-0051, §11 Q11). Until the lab confirms it, or
  while the connection lacks `AuditLog.Read.All`, age is the only trigger, and connection health
  says change monitoring is off. The permission is optional and recommended (threat model TM-D17
  rule 3, §6.6). With it, the same monitor also watches the bound Entra objects of technicians who
  hold correlation-derived grants, and alerts every `tenant-owner` to a Temporary Access Pass
  created, methods reset or registered by another actor, or the user's domain switching to
  federated (TM-D19 rule 4, activity names `[UNVERIFIED]`). Those signals only alert; the control
  is the authority factor (DM-30.I6).
- (e) Microsoft documents no default for either flag; the reference sample shows both `false`
  ([sync features](https://learn.microsoft.com/en-us/graph/api/resources/onpremisesdirectorysynchronizationfeature?view=graph-rest-1.0)).
  A new Entra connection therefore starts `unattested`, and its first attestation commonly finds
  a flag off (`open`) before the customer turns both on. The customer-visible prerequisite is
  stated in §10.
- (f) **First attested state.** `first_attested_at` is set once, by the first attestation that
  makes the state `attested`, and never changes afterwards. It splits the tenant's correlations for
  DM-20.I4(g): before it, the tenant is still being set up; after it, any state other than
  `attested` is a lapse.
**Lifecycle.** `draft → verifying → active ⇄ suspended → decommissioning → removed`. Verifying
checks reachability, identity and the delegated-rights limit (T-0007, ENH-08). Suspended stops
sync and writes. `takeover_protection` (Entra only, derived, I7) moves `unattested → open |
attested`, `open → attested`, and `attested → open | stale`; the common first path is `unattested
→ open → attested`, because both flags default to `false` (I7(e)). It leaves `open` or `stale`
only through a new attestation, which yields `attested` or `open`. The first move to `attested`
sets `first_attested_at` (I7(f)).

### DM-11 DirectoryCredential · T · owner `connector/credential` (SQL only in `credential/sealed`; written through `directory/connection`'s credential port, ADR-0003 rule 6)
**Definition.** The identity a connection uses against its directory. **Replaces (ME):** the
domain service-account and M365 app credentials, stored with AES-256 in ADMP
([data-security PDF](https://download.manageengine.com/products/ad-manager/encryption-and-data-storage-in-admanager-plus-database.pdf)).
**Key attributes:** `kind` (`gmsa`, `keytab_ref`, `ad_password`, `entra_certificate`,
`connector_local`) · public metadata (account or principal name, SID, Entra app/client ID, cert
thumbprint, `not_after`) · `sealed_secret` (only for `ad_password` and the Entra private key) ·
`key_version` · `state`.
**Invariants.** I1 Only code under `internal/connector/` unseals or uses it. API responses carry
metadata only (ADR-0002 rule 3, P3). I2 `gmsa` and `keytab_ref` hold no secret in the database.
`connector_local` means the secret lives on a remote connector's host. A SaaS AD connection is
always `connector_local`. I3 activeDIQ generates the Entra private key; the admin uploads only the
public certificate. I4 Rights are delegated only, with no Tier-0 or Entra privileged-role rights
(ADR-0002 rule 9).
**Lifecycle.** `pending` (key generated, awaiting consent or rights) `→ active → expiring`
(`not_after` within the reminder window) `→ rotated` (superseded) `| revoked`.

### DM-12 Component · T · owner `platform/fleet`
**Definition.** An enrolled remote process with its own mTLS identity. In v1 that is a remote
**connector**; from M3 also an **agent**. The embedded connector has no identity and is not a
Component (ADR-0002). One shape covers both kinds ("parameterise, don't clone").
**Key attributes:** `kind` (`connector`, `agent`) · `name` · host facts (hostname, OS, version) ·
`cert_serial` · `san_identity` (tenant + component) · `providers` (from `Describe`) ·
`server_endpoints` · `last_seen` · `state`. Sub-entity **EnrollmentToken**: `token_hash`,
`issued_by`, `expires_at`, `used_at`.
**Invariants.** I1 Enrolled to exactly one tenant. The tenant comes from the certificate, never
from a message. I2 An enrollment token is single-use, expiring, stored hashed, and issued by an
account holding the enrollment permission. I3 Certificate rotation keeps the Component identity.
**Lifecycle.** `pending` (token issued) `→ enrolled → active → revoked → removed`. Reachability is
health.

### DM-13 ConnectorBinding · T · owner `directory/connection` (ADR-0003 F1)
**Definition.** It routes a connection to the connector(s) that serve it. The binding is data, not
configuration (ADR-0002 rule 3). **Replaces (ME):** none (ADMP has no distributed connectors).
**Key attributes:** `connection_id` · `target` (`embedded` or a `component_id`) · `priority` · `state`.
**Invariants.** I1 Target and connection belong to the same tenant (composite FK). I2 A binding
is accepted only if the target's `Describe` reports a provider for the connection's kind. This is
why SaaS AD connections can never bind `embedded` (ADR-0002 P1). I3 Several bindings give
redundancy (ADM-210). Each operation item keeps one DC and one connector (read-your-writes).
**Lifecycle.** `active ⇄ disabled → removed`.

### DM-14 NamingContext · D · owner `directory/inventory`
**Definition.** A partition of an AD forest. **Domain** NCs hold managed objects. The
configuration and schema NCs are read for topology and the schema cache only. The configuration
NC's site objects are also read as Group Policy SOMs (DM-23.I4). The equivalent for
an Entra connection is the tenant itself, so it has no NamingContext rows. **Replaces (ME):** a
managed "domain" (ADM-212, ADM §2.9).
**Key attributes:** `nc_guid` (NC head objectGUID) · `kind` (domain, configuration, schema,
application) · `dns_name` and `netbios_name` (snapshots) · `domain_sid` · `functional_level` ·
`managed`.
**Invariants.** I1 Only domain NCs can be `managed`. I2 Deletion lifetimes and the Recycle Bin
flag are forest-wide and live on the Connection (DM-10.I6), never per NC.
**Lifecycle.** `discovered → managed ⇄ unmanaged → gone`.

### DM-15 DomainController · D · owner `directory/inventory`
**Definition.** A DC of a managed domain, as discovered from the configuration NC and DNS.
**Key attributes:** `dsa_guid` (objectGUID of its NTDS Settings object; the stable DC identity) ·
`invocation_id` (replication identity; changes on restore and when the VM-GenerationID changes,
[virtualized DC](https://learn.microsoft.com/en-us/windows-server/identity/ad-ds/get-started/virtual-dc/virtualized-domain-controller-architecture)) ·
`dns_hostname` · `site` · `is_gc` · `is_rodc` · `os_version` · admin flags (`excluded`,
`priority`) · `last_seen`.
**Invariants.** I1 Per-DC values (e.g. `lastLogon`, ADM-084) are keyed by `dsa_guid`.
I2 An RODC is never a write target. I3 An operation pins one writable DC per naming context it
reads or writes; Plan, the Apply re-check, the write and Verify go to that pin. If the pin stays
unavailable past the verify window, Verify reads back from another DC, recorded by name
(DM-42.I3, ADR-0005 rule 5). I4 Demoting and re-promoting a server creates a new NTDS Settings object, so it is a **new**
DC row with a new `dsa_guid`, even under the same hostname. I5 Any USN-based position is keyed by
`(dsa_guid, invocation_id)`. A changed `invocation_id` invalidates it.
**Lifecycle.** `discovered → in_use | excluded → retired`.

### DM-16 DirectoryObject · D · owner `directory/inventory`
**Definition.** The current, last-observed state of one AD or Entra object: user, inetOrgPerson,
group, computer, contact, OU, container, gMSA, foreign security principal, or another class
carried as data. **Replaces (ME):** the objects behind every Management tab (ADM-008…062), AD
Explorer (ADM-004) and the M365 objects (ADM-160…164).
**Key attributes:** `object_guid` · `connection_id` · `nc_guid` · `object_class` (most specific
structural class) and `kind` · `parent_guid` · `ancestry` (GUID path to the NC head) · `dn` and
`rdn` (display snapshot) · `sid` (security principals) · `sam_account_name` · `upn` ·
`display_name` · `enabled` (from `userAccountControl`) · time-dependent state *inputs*:
`lockout_time`, `pwd_last_set`, `account_expires`, and the effective password policy (domain
policy or PSO) · `tier0` (definition: T-0007) · typed values of the synced attribute set ·
`when_created` · `when_changed` · `observed_at` + `observed_dsa` · `cloud_seen_at` (Entra users
and groups only, I9) · `state`.
**Invariants.**
- I1 Identity is the GUID (X3). A rename, a move, or a cross-domain move within the forest changes
  `dn`, `parent_guid`, `ancestry`, `nc_guid` and, for a cross-domain move, `sid` (the old SID goes
  to `sIDHistory`). It never changes identity. A cross-domain move expunges the object from the
  source NC and leaves only an `infrastructureUpdate` proxy there
  ([cross-NC move](https://learn.microsoft.com/en-us/openspecs/windows_protocols/MS-ADTS/8bcbd10f-f98b-4881-84b0-290db509cc18)).
  So sync treats an add of a known GUID in another NC as a **move**, never a delete plus a create,
  and a resync diffs the whole forest by GUID, never one NC at a time `[LAB: Windows]`.
- I2 `dn` is display-only and is refreshed on every observation.
- I3 Secret attributes are never stored (X4, safe-primitives LF-38).
- I4 There is one current row per identity. Its past values live in ChangeRecord (DM-18).
- I5 Values carry freshness (`observed_at`, source DC). Last logon is per-DC or labelled with
  `lastLogonTimestamp`'s lag.
- I5a Time-dependent state is never stored as a flag. A lockout expiring or a password expiring
  involves no directory write, so sync never sees it, and `lockoutTime` is not reset to 0 when the
  lockout duration passes ([lockoutTime](https://learn.microsoft.com/en-us/windows/win32/adschema/a-lockouttime)).
  `locked_out`, `password_expired`, `password_expires_at` and `account_expired` are computed at
  read time from the stored inputs and the effective policy. A decision that acts on them (unlock,
  reset, a leaver policy) re-reads `msDS-User-Account-Control-Computed` and
  `msDS-UserPasswordExpiryTimeComputed` live at Plan `[LAB: Windows]`.
- I6 AD and Entra objects are never merged. A hybrid user is two rows joined by a Correlation
  (DM-20).
- I7 Uniqueness (sAMAccountName, UPN, CN in a container) is decided by the DC, not by this table
  (safe-primitives R9).
- I8 `tier0` objects are outside every write scope in v1 (DM-35.I5).
- I9 **Cloud observation (Entra only).** `cloud_seen_at` is the latest time sync observed the
  Entra object as cloud-only (`onPremisesSyncEnabled` not `true`) or cloud-managed
  (`onPremisesSyncBehavior.isCloudManaged` is `true`). It is set from the first sync onwards, also
  for an object no correlation points at yet, and is never cleared while the object exists. A
  takeover turns a cloud-only object into a synced one, so this observation usually predates the
  correlation it later forms; that is why it lives on the object and not on the correlation. It
  feeds DM-20.I4(g).

**Lifecycle (AD).**

```
 live --delete--> deleted --(msDS-deletedObjectLifetime)--> recycled --(tombstoneLifetime)--> purged
  ^                  |                                       (Recycle Bin on; isRecycled: never restorable)
  +----restore-------+   restore keeps objectGUID and objectSid; links and attributes come back
 live --delete--> tombstone --(tombstoneLifetime)--> purged      (Recycle Bin off)
  ^                  |
  +--reanimate-------+   keeps objectGUID, objectSid, sIDHistory and searchFlags-0x8 attributes; every link value is lost
 any --moved into an unmanaged NC / NC unmanaged--> out_of_scope --back in scope--> live
```

`purged` keeps the history rows and a final ChangeRecord. With the Recycle Bin, restored users
"regain all group memberships" ([Recycle Bin](https://learn.microsoft.com/en-us/windows-server/identity/ad-ds/get-started/adac/active-directory-recycle-bin)).
Restore rules `[LAB: Windows]`
([tombstone and recycled objects](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-adts/4302a2eb-55c8-426c-b310-6791c6ae8307)):
a recycled object (`isRecycled`) cannot be undeleted at all. A restore needs a live parent (the
object's `lastKnownParent`, or a restored one). An object deleted before the Recycle Bin was
enabled is a tombstone and only reanimates, with the losses shown above.
**Lifecycle (Entra).** `active → soft_deleted → purged`, and `soft_deleted → active` on restore.
Restorable for 30 days: users, Microsoft 365 groups (assigned and dynamic), cloud security groups
(preview, public clouds), applications, service principals and administrative units
([restore groups](https://learn.microsoft.com/en-us/entra/identity/users/groups-restore-deleted),
[deleted items](https://learn.microsoft.com/en-us/graph/api/resources/directory?view=graph-rest-1.0)).
Distribution groups are not restorable, so their delete goes straight to `purged`. activeDIQ restores a
synced object in AD, its source of authority, and never through Entra. Whether Entra deleted items
can restore a synced group at all is `[UNVERIFIED]`. In a delta feed, `@removed.reason: changed` maps to `soft_deleted` and `deleted`
maps to `purged` ([delta query](https://learn.microsoft.com/en-us/graph/delta-query-overview)).

### DM-17 Link · D · owner `directory/inventory`
**Definition.** One value of a linked attribute (`member`, `manager`, …), stored as a directed edge
between GUIDs. For Entra it is one value of a directory relationship: the `members` of a group or
of an administrative unit, or `manager`. **Replaces (ME):** membership management (ADM-050) and the manager field (ADM-033).
**Key attributes:** `source_guid` · `link_attr` · `target_guid`, or `target_unresolved` (a SID for a
foreign security principal not yet resolved, or a DN outside every managed NC, as a snapshot) ·
`state` · `observed_at`.
**Invariants.** I1 Only forward links are stored. Back-links (`memberOf`, `directReports`) are
derived ([linked attributes](https://learn.microsoft.com/en-us/windows/win32/ad/linked-attributes)).
I2 The primary group is its own edge kind, derived from `primaryGroupID`, because it is absent from
`member`. I3 Group nesting may cycle, so every transitive traversal carries a visited set.
I4 A cross-forest member is an edge to a foreign security principal object. Resolving it to the
other forest's object is a lookup recorded on the edge, never a merge. FSPs also stand for
well-known SIDs such as Authenticated Users, which resolve to no object. A member from another
domain of the *same* forest is an ordinary DN value to a real object, never an FSP
([foreignSecurityPrincipal](https://learn.microsoft.com/en-us/windows/win32/adschema/c-foreignsecurityprincipal)).
**Lifecycle.** `active → deactivated` (target deleted with the Recycle Bin on) `→ active`
(restore), or `→ removed`. With the Recycle Bin off, a deleted target's links are removed, not
deactivated, and a reanimation does not bring them back `[LAB: Windows]`. Every transition writes
a ChangeRecord.

### DM-18 ChangeRecord · D · append-only · owner `directory/inventory`
**Definition.** One observed change to one attribute or link value of one object. This is the
history built for audit queries over years (blueprint §12). **Replaces (ME):** the object History
tab (ADM-005), and from M3 part of the Backup Explorer (ADM-150).
**Key attributes:** `object_guid` · `connection_id` · `attribute` (or link attr + target) · `old` ·
`new` · `observed_at` · `origin` (nullable: originating DSA invocationId, originating USN,
originating time and version, from `msDS-ReplAttributeMetaData` and
[`msDS-ReplValueMetaData`](https://learn.microsoft.com/en-us/windows/win32/adschema/a-msds-replvaluemetadata)) ·
`source` (`sync`, `operation:<id>/<item>`, or `event:<id>` from M3) · `actor` (only when the
source is an operation).
**Invariants.** I1 Append-only (X5). It is partitioned by time and retained per tenant
(ADM-206). I2 It is observation-based: a value that changed twice between two observations shows
as one change, and the UI says so. DirSync returns final state only, never old values, so `old`
comes from our previous observation. I2a `origin` is null for link values written before
linked-value replication was enabled (legacy values carry no value metadata)
`[LAB: Windows]`. The originating time is the originating DC's clock and is labelled as such,
never presented as our observation time. I3 v1 never attributes a native (non-activeDIQ) change to a
person. That arrives with DC events (M3). I4 Secret attributes are never recorded. I5 It is
indexed for three questions: everything about object X, every change to attribute A in a period,
and everything operation O did. I6 Values of personal attributes are erasable under X11 without
updating the row.
**Lifecycle.** `recorded → archived → purged`, all derived (X5). `archived` means the row's time
partition has been exported to the archive. `purged` means the retention role dropped that
partition. No row ever changes state in place.

### DM-19 SyncCursor · T · owner `directory/sync`
**Definition.** The change-feed position for one partition: an AD domain NC (DirSync) or one Graph
resource of an Entra tenant (delta).
**Key attributes:** `connection_id` · `partition` (NC GUID or Graph resource) · `cookie` (opaque) ·
`issuing_dsa_guid` (AD: the DC that issued the cookie) · `last_full_sync_at` · `last_change_at` ·
`lease_fencing_token` · `state`.
**Invariants.** I1 It is written in the same transaction as the inventory rows it covers
(blueprint §14 flow 1). I2 One reader per partition holds the lease (DM-06). I3 An invalid or
expired cookie forces a full resync. That resync diffs against inventory forest-wide by GUID
(DM-16.I1), so deletions missed while the cookie was stale still become `deleted` or `purged`.
I4 A DirSync cookie is reused only on the DC that issued it. On another DC it may replay changes,
return everything, or be rejected with `0000203D`. All three outcomes end in `resync_required`
([DirSync](https://learn.microsoft.com/en-us/windows/win32/ad/polling-for-changes-using-the-dirsync-control)).
I5 DirSync does not report the children of a moved or renamed parent. Their `dn` and `ancestry`
are re-derived from the parent's new position, not awaited from the feed. I6 A Graph delta token
expires after 7 days (`syncStateNotFound`), and `410 Gone` also means a full sync
([delta query](https://learn.microsoft.com/en-us/graph/delta-query-overview)). The AD reader
contract (show-deleted control `1.2.840.113556.1.4.417` with DirSync, an `objectClass` filter
rather than `objectCategory`, and `isDeleted` requested) belongs to T-0018.
**Lifecycle.** `initial_sync → incremental ⇄ resync_required`. It is `paused` while the connection
is suspended.

### DM-20 Correlation · D · owner `directory/inventory`
**Definition.** It asserts that an AD object and an Entra object are the same identity. Only a
`matched` correlation carries authority or write routing across the two directories (I4).
**Replaces (ME):** the hybrid handling behind ADM-169.
**Key attributes:** `ad_ref` · `entra_ref` · `anchor_attr` (`objectGUID`, `ms-DS-ConsistencyGuid`,
or another attribute) · `anchor_value` · `match` (`anchor`, or `sid` via
`onPremisesSecurityIdentifier`) · `state` · `candidate_reason` (`not_synced`, `cloud_managed`,
`sid_mismatch`, `domain_mismatch`, `link_unconfirmed`, `ambiguous_anchor`,
`tenant_takeover_open`, `reconfirm_required`) · `gate_checked_at` · `eligible_since` and
`eligibility_class` (`install_time`, `attested`, `lapsed`; both set once, I4(g)) ·
`reconfirmed_by` and `reconfirmed_at` (I4(g)). `source_of_authority` is derived from the state and
is never stored. It is `ad` while `matched`. While `candidate`, nothing is routed to AD on the
object's behalf, and the Entra object is planned as an Entra object alone, within its own Entra
scope.
**Invariants.**
- I1 A correlation is made only from the source anchor or the SID, never from name or UPN
  heuristics ([sourceAnchor](https://learn.microsoft.com/en-us/entra/identity/hybrid/connect/plan-connect-design-concepts)).
  For users, `onPremisesImmutableId` is the base64 of a binary anchor (objectGUID,
  ms-DS-ConsistencyGuid). A string anchor such as employeeID is used as is.
- I1a Users match `ms-DS-ConsistencyGuid` first, then `objectGUID`. After a forest migration the
  anchor can be the *old* forest's GUID, carried in ms-DS-ConsistencyGuid. With the ConsistencyGuid
  option, Entra Connect uses ms-DS-ConsistencyGuid for users and objectGUID for other types. Cloud
  Sync uses ms-DS-ConsistencyGuid when present, else objectGUID, and that choice cannot be changed
  ([Cloud Sync topologies](https://learn.microsoft.com/en-us/entra/identity/hybrid/cloud-sync/plan-cloud-sync-topologies)).
  The anchor is therefore looked up by both `objectGUID` and `ms-DS-ConsistencyGuid`, across every
  AD connection that has a HybridLink (DM-21) to the tenant. In an account-and-resource-forest
  topology, the sign-in attributes, including the source anchor, come from the forest that holds
  the enabled account, so the correlation targets that forest's object
  ([default sync configuration](https://learn.microsoft.com/en-us/entra/identity/hybrid/connect/concept-azure-ad-connect-sync-default-configuration)).
- I1b Groups have no `onPremisesImmutableId`. They match on `onPremisesSecurityIdentifier` (the AD
  group's SID) ([group](https://learn.microsoft.com/en-us/graph/api/resources/group?view=graph-rest-1.0)).
  A cross-domain move changes the SID (DM-16.I1), so the correlation goes `broken` until
  `onPremisesSecurityIdentifier` carries the new SID. It is never re-matched by name.
- I2 There is at most one Entra object per AD object per Entra tenant.
- I3 While `matched`, writes to attributes whose source of authority is AD go to AD, and
  Entra-only attributes (licences) go to Graph. A `candidate` routes nothing to AD.
- I4 **Authorizing gate.** A correlation is `matched` only while **all** of the following hold.
  Otherwise it is `candidate`: shown in the UI as a possible match with its reason, and never used
  by DM-30.I5, DM-35.I6, DM-36.I2 or I3. `candidate_reason` names the first check that fails, in
  the order listed. The threat model confirms (a)–(f) and adds (g) (TM-D17,
  [threat model §6.8](../architecture/threat-model.md)). A correlation that rests on a value a privileged Entra
  admin can write is never evidence of authority.
  - (a) The Entra object's `onPremisesSyncEnabled` is `true`. It is read-only in Graph, whereas
    `onPremisesImmutableId` can be written by certain privileged admin roles
    ([user](https://learn.microsoft.com/en-us/graph/api/resources/user?view=graph-rest-1.0)).
    `null` means never synced, source of authority (SOA) transferred to the cloud, or an SOA
    rollback still waiting for the sync client. `false` means no longer synced.
  - (b) `onPremisesSyncBehavior.isCloudManaged` is not `true`. After an SOA transfer of a user or
    group it is `true`, `onPremisesSyncEnabled` is `null` and the sync client stops flowing
    changes ([user SOA](https://learn.microsoft.com/en-us/entra/identity/hybrid/how-to-user-source-of-authority-configure)),
    so (a) already fails; (b) is the second check. The property is beta
    ([onPremisesSyncBehavior](https://learn.microsoft.com/en-us/graph/api/resources/onpremisessyncbehavior)).
    When it cannot be read, (a) alone decides.
  - (c) For users, `onPremisesSecurityIdentifier` equals the AD object's current `objectSid`. The
    sync client writes it from the AD object, so it corroborates an anchor that an Entra admin, or
    the admin of another forest synced into the same tenant, could copy. Admins can write it only
    after an SOA transfer, which (a) excludes. For groups the SID is the match itself (I1b).
    Whether Cloud Sync populates it for users is `[UNVERIFIED]`. Until the lab confirms it
    (T-0051), a Cloud Sync user without it stays `candidate` (`sid_mismatch`).
  - (d) `onPremisesDomainName`, where populated, equals the DNS name of the AD object's domain,
    and the HybridLink between that domain and the tenant is `confirmed` (DM-21.I2).
  - (e) The anchor resolves to exactly one AD object (I1a lookup). If an anchor matches two, for
    example because a second forest stamped a copied GUID into its own `ms-DS-ConsistencyGuid`,
    every correlation on it is `candidate` (`ambiguous_anchor`).
  - (f) The tenant blocks cloud-object takeover:
    `blockCloudObjectTakeoverThroughHardMatchEnabled` and `blockSoftMatchEnabled` are both `true`
    ([sync features](https://learn.microsoft.com/en-us/graph/api/resources/onpremisesdirectorysynchronizationfeature?view=graph-rest-1.0)),
    **as attested**: the Entra connection's `takeover_protection` is `attested` (DM-10.I7).
    activeDIQ cannot read the flags live, because Graph lets only a signed-in Global
    Administrator read them. Without (f), an Entra admin can pre-create a cloud user that carries
    a target's anchor (hard match) or UPN (soft match). When the target enters sync scope, the sync
    client takes the cloud object over. (a)–(e) then pass, and the sign-in methods the attacker
    registered stay on the object. While the tenant is not `attested`, the connection's health
    says why and every correlation in that tenant is `candidate` (`tenant_takeover_open`).
    Microsoft recommends keeping soft-match blocking on except while soft matching is needed
    (same source).
  - (g) **Eligibility only goes down** (TM-D17 rule 4). The correlation is *eligible* while
    (a)–(e) hold. `eligible_since` is the time it first became eligible, and `eligibility_class`
    records the Entra connection's situation at that moment (DM-10.I7): `install_time` if
    `first_attested_at` was still unset, `attested` if `takeover_protection` was `attested`, and
    `lapsed` otherwise (`open` or `stale` after the first attestation). A **re-confirmation** is
    required while either holds:
    - the Entra object's `cloud_seen_at` (DM-16.I9) is set and `reconfirmed_at` is unset or
      earlier. Our sync once saw the object cloud-only or cloud-managed, so a takeover may have
      happened, even if both tenant flags are on again by now;
    - `eligibility_class` is `lapsed` and `reconfirmed_at` is unset. The correlation formed while
      an attestation had lapsed.

    While one is required, the correlation is `candidate` (`reconfirm_required`), even when
    (a)–(f) pass. Only a `tenant-owner` re-confirms, with step-up (threat model §7.4), in an
    audited Operation with one item per correlation that shows why it is needed. The Operation
    sets `reconfirmed_by` and `reconfirmed_at`. A later cloud observation requires a new
    re-confirmation. `eligible_since` and `eligibility_class` are set once. They and the latest
    re-confirmation survive `broken` (Lifecycle), so leaving and re-entering the gate never resets
    them.
    **The install-time population** (`install_time`) is `candidate` (`tenant_takeover_open`)
    until the tenant's first `attested` state. It then becomes `matched` with no re-confirmation,
    unless the first bullet applies. A new hybrid tenant can hold thousands of these, and a review
    one by one would become a rubber stamp. Takeovers among them that our sync never observed are
    the threat model's residual TM-R11. AD-side authority still needs the AD-anchored authority
    factor (DM-30.I6).
- I5 **Re-check.** Sync evaluates the gate whenever either side changes. It is evaluated again at
  sign-in (DM-30.I5), and at Plan for every Operation whose scope or grant passes through the
  correlation. At those two points the sources differ by check:
  - (a)–(e) are re-read live: the Entra object through Graph, the AD side through LDAP.
  - (f) is taken from the connection's current `takeover_protection` (DM-10.I7), which is computed
    from the latest attestation and is never read live.
  - (g) is taken from the stored `cloud_seen_at`, `eligibility_class` and `reconfirmed_at`. A live
    read of (a) or (b) that sees the object cloud-only or cloud-managed also updates
    `cloud_seen_at` through the targeted re-sync below.

  A failed check refuses that sign-in grant or plans the item as `blocked`. The failure is audited
  and requests a targeted re-sync of both objects. The stored state changes only through sync
  (kind `D`). A Request whose plan depended on the correlation fails `stale_state` at apply
  (DM-42.I2) if the gate fails by then. After a cross-domain move, (c) fails closed until a sync
  cycle carries the new SID.
- I6 **Residual risk, closed by the threat model.**
  - **Sync plane.** Anyone who controls the sync client (the Entra Connect server, a Cloud Sync
    agent host, the Directory Synchronization Accounts role) can make (a)–(e) pass. So can anyone
    who can change the tenant's sync features (f), or transfer SOA (Hybrid Administrator). The gate
    cannot defend against these. They are Tier 0: customer-designated hosts and Entra roles in
    `tier0` (threat model §6.4, E4), activeDIQ never holds a permission that does any of them
    (§6.6 deny list), and the rest is TM-R11. Takeovers that happened before installation, or in
    the install-time population without a cloud observation (I4(g)), are TM-R11 too.
  - **Authentication plane.** A `matched` correlation is legitimate, yet whoever can sign in to
    Entra as the synced technician would inherit the AD-side group grants that reach the `sso`
    account through it (DM-30.I5, DM-36.I2).
    - A Privileged Authentication Administrator can issue a Temporary Access Pass to any user, or
      reset their methods. An Authentication Administrator can do the same for non-admin users,
      and activeDIQ technicians are often non-admins in Entra. The Authentication Policy
      Administrator decides who may sign in with a pass
      ([TAP](https://learn.microsoft.com/en-us/entra/identity/authentication/howto-authentication-temporary-access-pass)).
      A pass holder can register a passkey, so an authentication strength does not stop this.
    - A Hybrid Identity Administrator manages federation settings
      ([roles](https://learn.microsoft.com/en-us/entra/identity/role-based-access-control/permissions-reference)),
      and the identity provider of a federated domain signs in that domain's users.
    - **History.** An attestation speaks only for the present. An object taken over while the
      flags were off keeps the methods registered on it.

    The threat model closes all three with TM-D19 (§6.9): correlation-derived AD-side grants need
    an activeDIQ-held authority factor enrolled with AD-plane proof or `tenant-owner` approval
    (DM-30.I6, DM-37.I3), and console-backing objects are escalation objects (DM-30.I7). Its
    residual, one person controlling both planes at enrolment, is TM-R12.
- I7 **Authority that never crosses** (TM-D17 rule 5). Whatever its state, a correlation never
  carries `tenant-owner` or any `control_plane` permission (DM-33.I3). Those are assigned only to
  the console account itself, through a RoleAssignment whose subject is that account. A group or
  automation-policy subject can never hold them, in either directory, so no membership and no
  correlation can confer them (DM-36.I4). A correlation never brings a
  `tier0` object into reach on either side. An AD object with **any** correlation (`candidate`,
  `matched` or `broken`) to an Entra `tier0` principal is itself `tier0`, and so is an Entra
  object with any correlation to an AD `tier0` object (threat model §6.4 C16 and E5; DM-35.I5).
**Lifecycle.** `candidate ⇄ matched` (the I4 gate, evaluated per I5). Every new correlation starts
as `candidate`. `candidate → matched` happens only when the whole gate (a)–(g) passes. For class
`attested`, that is as soon as (a)–(f) pass. For `install_time`, it is when the tenant's first
`attested` state arrives. For `lapsed`, or after a cloud observation, it needs a `tenant-owner`
re-confirmation first. `matched → candidate` happens whenever any check fails. Either state goes
`→ broken` when one side is purged or the anchor or group SID no longer matches. A `broken`
correlation returns only through I1, and only to `candidate`, never straight to `matched`. It keeps
its I4(g) markers. A correlation re-formed later for the same AD and Entra objects inherits them
too. `→ removed`.

### DM-21 HybridLink · T · owner `directory/connection` (ADR-0003 F1)
**Definition.** It declares which AD domain syncs into which Entra tenant. The relation is
many-to-many. **Replaces (ME):** the domain↔tenant links (ADM-159).
**Key attributes:** `ad_connection_id` + `nc_guid` · `entra_connection_id` · `origin` (declared,
or discovered from correlations) · `state`.
**Invariants.** I1 It decides which Entra tenant receives the M365 steps of a user create
(ADM-027). I2 A link discovered from correlations stays `proposed` until it is confirmed in an
audited Operation. Only a `confirmed` link lets correlations between that domain and that tenant
authorize (DM-20.I4), so discovery can never bootstrap its own trust. Confirming a link switches
on cross-directory authority. So confirming, or declaring a link (which creates it `confirmed`),
requires `connections.hybrid_link.confirm` held over **both** sides: an assignment scope that covers
the domain's `naming_context`, and one that covers the tenant's `entra_tenant` root (DM-35).
`tenant-owner` also qualifies. No narrower scope is enough.
**Lifecycle.** `proposed → confirmed → removed`.

### DM-23 GpLink · D · owner `directory/inventory`
**Definition.** One link from a scope of management (SOM: a domain, an OU or a site) to a Group
Policy Object. It is derived at sync from the SOM's `gPLink` value. `gPLink` is a single-valued
Unicode string with no Link-Id, not a linked attribute
([gPLink](https://learn.microsoft.com/en-us/windows/win32/adschema/a-gplink)), so DM-17 does not
cover it. Its value is `[<GPO DN>;<options>][<GPO DN>;<options>]…`. The order of the entries is
the link order. Option `0x1` means the link is ignored (disabled), and `0x2` means enforced, which
has no effect when `0x1` is set. `gPOptions = 1` on a domain or OU blocks inheritance of
non-enforced links from above
([MS-GPOL Domain SOM Search](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-gpol/08090b22-bc16-49f4-8e10-f27a8fb16d18)).
The **GPO** itself is a DirectoryObject (DM-16) of class `groupPolicyContainer`. Its synced
attributes include `displayName`, `flags` (user or computer settings disabled), `versionNumber`,
`gPCFileSysPath`, the extension-name lists and `gPCWQLFilter`. **Replaces (ME):** GPO link
management (ADM-073), "where is this GPO linked" (ADM-077) and unlinked GPOs (ADM-148).
**Key attributes:** `som_guid` · `position` (index of the entry in the SOM's `gPLink` value) ·
`gpo_guid` (objectGUID of the `groupPolicyContainer`) or `gpo_unresolved` (the DN snapshot, for a
GPO that does not exist or lies outside every NC we read) · `gpo_dn` (snapshot) · `enabled`
(`0x1` clear) · `enforced` (`0x2` set and `0x1` clear) · `observed_at` · `state`. The SOM's own
DirectoryObject row carries `gp_link_raw` (the whole observed `gPLink` value, used for the
stale-state check) and `block_inheritance` (`gPOptions`; domains and OUs only).
**Invariants.**
- I1 The value is parsed by a codec built on the P2 DN parser (safe-primitives §4), never by
  string matching or formatting. Each GPO DN is resolved to the GPC's objectGUID, and the edge
  stores that GUID (X3). The DN names the GPO by its `cn` (`{GPO ID}`), which is **not** its
  objectGUID, so the two are never compared. Each entry starts with an `LDAP://` prefix, which is
  stripped (case-insensitively) before the DN is parsed. A DN that resolves to nothing, including
  a GPO in another forest, is kept as `gpo_unresolved` and shown as a broken link, never dropped.
- I2 Position is data. The same GPO may be linked more than once to one SOM, with independent
  options, so the edge key is `(som_guid, position)`, never `(som_guid, gpo_guid)`. GPMC's link
  order is derived from `position`. Link order 1 (highest precedence) is the **last** entry in the
  string, and link order n is the first. MS-GPOL states only that the order is the link order;
  the direction comes from an SSSD fix checked against GPMC
  ([SSSD commit](https://github.com/SSSD/sssd/commit/dce025b882db7247571b135e928afb47f069a60f))
  `[UNVERIFIED]` `[LAB: Windows]`. The reorder Action does not ship until the lab confirms it (T-0051).
  An edge has no identity beyond its key. Edges are a projection of the SOM's current `gPLink`
  value: every observed change replaces the SOM's whole edge set, so inserting a link at the front
  re-creates every edge rather than renumbering it. Nothing references an edge by key. An
  Operation item plans against the SOM GUID and `gp_link_raw` (I3), and the link history is the
  ChangeRecord on the SOM's `gPLink` attribute (old and new values).
- I3 Every link write (link, unlink, enable, disable, enforce, reorder) rewrites the whole value,
  and so does block inheritance on `gPOptions`. The Action plans against `gp_link_raw` and applies
  as **one** LDAP modify that deletes the exact planned value and adds the new one. If anyone
  changed the value since the plan, the modify fails and the item fails `stale_state` (DM-42.I2),
  instead of silently dropping someone else's link. LDAP modify is atomic, and deleting a value
  that is not present fails with `noSuchAttribute`
  ([RFC 4511 §4.6](https://www.rfc-editor.org/rfc/rfc4511#section-4.6)). The same holds for the
  integer `gPOptions`. These writes never send the permissive-modify control
  (`1.2.840.113556.1.4.1413`), because it turns the failed delete into a success and breaks the
  compare. When the value was absent at plan, the write is an add-only modify, which fails if a
  value appeared in the meantime (the exact error code is `[UNVERIFIED]`). An absent `gPOptions`
  means 0 `[LAB: Windows]`. A read-modify-write without this compare is forbidden.
- I4 Site SOMs live in the configuration NC (`CN=Sites,CN=Configuration,…`). The configuration NC
  is not managed (DM-14.I1), but its site objects are read as SOMs. A site link applies to every
  computer in the site, in every domain. `gPOptions` matters only on domains and OUs. The site is
  added last to the SOM list, so there is nothing above it to block, but block inheritance on a
  domain does block site links
  ([MS-GPOL SOM list](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-gpol/bf1f9c51-6674-4b74-b0d7-635f1121aeec)).
- I5 A link write changes policy for everything the SOM reaches, so it is in write scope only if
  the SOM is in scope (DM-35) **and** nothing it reaches is `tier0`. Reach is the SOM's whole
  subtree; for a domain head that includes non-OU containers such as `CN=Users`. Reach ignores
  block inheritance, because enforced links pass through it. It includes `tier0` accounts, since
  user settings apply when they log on, and computers that use loopback processing
  ([MS-GPOL loopback](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-gpol/595ec4ac-95eb-4d56-bec6-aed0e47fb202)).
  A link on the domain head, on an OU that holds a DC, or on a site that holds a DC (a DC's server
  object sits under that site) applies to DCs. Such a link write is a Tier-0 write, outside every
  v1 write scope (DM-16.I8, Q1).
- I6 "Unlinked" (ADM-148) means no edge from any SOM in any domain or site of the forest, because
  a GPO can be linked from another domain. Links in unmanaged domains are invisible to us, so the
  result names the NCs it covered and never claims more.
- I7 GPO permissions (ADM-077 "GPO delegation") are two ACLs: the GPC's `nTSecurityDescriptor`
  in AD and the GPT folder's DACL in SYSVOL. GPMC keeps them consistent. v1 has no SYSVOL path,
  so v1 reads GPO delegation (from the GPC, through the typed security-descriptor primitive) but
  has no permission-write Action until Q10 is decided. Security filtering checks only the
  Apply Group Policy right on the GPC
  ([MS-GPOL security filtering](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-gpol/5ead679e-5ec1-4f43-b927-1a339da316c7)).
  But a client opens `gpt.ini` for every GPO it finds and stops processing on any error, so a
  change to the GPC alone can break policy for that target. v1 cannot see drift between the GPC
  and the GPT, and the UI says so.

**Lifecycle.** `active ⇄ broken` (the GPO DN stops or starts resolving) `→ removed` (unlinked, or
the SOM is deleted). Enabled and enforced are attributes, not states. Every change is a
ChangeRecord on the SOM's `gPLink` attribute, holding the old and new values.

## 3. Identity and access

### DM-30 Account · T · owner `platform/authn`
**Definition.** A human who signs in to the console or API: a technician, an administrator or a
workflow requester. **Replaces (ME):** the technician (ADM-126) and workflow requester accounts
(ADM-117).
**Key attributes:** `kind` (`local`, `sso` with issuer+subject, `directory` with
connection+GUID) · `directory_ref` (connection+GUID: required for `directory`, optional for `sso`,
null for `local`) · `display_name` · `email` · `mfa_required` · `state` · `created_by`.
**Invariants.** I1 Local accounts always require MFA (ADM-142). I2 A `directory` account is
disabled, and its sessions revoked, when sync observes the AD user disabled or deleted, or out of
every scope the account was admitted through. Sign-in also refuses it when `accountExpires` is in
the past, checked at every sign-in, because expiry involves no directory write
([accountExpires](https://learn.microsoft.com/en-us/windows/win32/adschema/a-accountexpires)). I3 There
are no default credentials: the first account is created with a one-time bootstrap secret at
install (ADM-145). I4 A tenant always has at least one active account holding `tenant-owner`, so
the last one cannot be removed. This is enforceable because `tenant-owner` is held only through an
assignment to the account itself (DM-36.I4): no membership change made outside activeDIQ can
remove an owner. I5 **SSO accounts and the directory.** An `sso` account gets a
`directory_ref` only from an anchor claim that the tenant's SSO configuration names: the Entra
object ID `oid`, with `tid` matching an Entra connection, or the on-premises SID (Entra's
`onprem_sid` optional claim, present only for synced users,
[optional claims](https://learn.microsoft.com/en-us/entra/identity-platform/optional-claims-reference)).
A SID changes on a cross-domain move, so it is resolved once when the account is bound, and the
GUID is stored (X3). A UPN, email or name claim never binds, because they are reassignable. The
immutable ID does not bind either: there is no standard claim for it `[UNVERIFIED]`, and it can be
written for cloud users ([user](https://learn.microsoft.com/en-us/graph/api/resources/user)). A later sign-in whose anchor
resolves to a different object is refused and audited. It never rebinds silently; rebinding is an
audited administrative action. A binding never crosses directories on its own. Bound by `oid`, the
account reaches AD-side group grants only through a `matched` correlation of that Entra object
(DM-20.I4). Bound by `onprem_sid`, the binding holds only while the signing-in Entra object has a
`matched` correlation to the AD object the SID resolves to. Both are re-checked at every sign-in
and at Plan (DM-20.I5). A bound `sso` account receives group-subject grants (DM-36.I2) and
falls under I2 exactly like a `directory` account. An unbound one receives only grants made to the
account itself. `authn` reads anchors and correlations only through its port
`authn.DirectoryAnchors`, which `directory/inventory` implements (ADR-0003 F6, blueprint §7.5).
I6 **Authority factor** (threat model TM-D19 rules 1–3). A bound `sso` account signs in through Entra. It uses correlation-derived grants (DM-36.I2), meaning the AD-side group
grants that reach it through an `oid` or `onprem_sid` binding, only in a session that has verified
one of its authority factors (DM-37.I3). The factor is checked at first use in the session and again
at every step-up (threat model §7.4), and the session records it (DM-31.I3). Where the PRD offers
SPNEGO sign-in, a session that authenticated the correlated AD account by Kerberos counts instead
`[OPEN → ADM-143 spec]`. Without either, the session keeps its Entra-side grants and the grants
made to the account itself. This is the same degraded mode as an unattested tenant, so nothing
breaks. Each refused use is audited with reason `authority_factor_missing`. A `directory` account
already authenticates through the AD plane, so this rule adds nothing for it. I7 **Console-backing
objects are escalation objects** (TM-D19 rule 5). The following objects back a console account:
- the AD object of a `directory` account;
- the object an `sso` account is bound to;
- any object with a correlation (DM-20), in any state except `removed`, to either.

Through activeDIQ, some changes to such an object need an actor who holds every privilege the
backed account holds, over every scope it holds it (the DM-36.I1 test). Those changes are a
password reset, an unlock, enabling the object, a change of its UPN or `sAMAccountName`, and a
move. Without that, Plan refuses the item and the refusal is audited. The Entra app never writes
authentication methods (threat model §6.6 deny list).
**Lifecycle.** `invited → active ⇄ disabled → deleted`. Audit keeps the ID and a name snapshot,
which is erasable under X11.

### DM-31 Session · T · owner `platform/authn`
**Definition.** An authenticated console session, kept in PostgreSQL so any node serves it.
**Key attributes:** `id_hash` · `account_id` · `methods` · `mfa_at` · `authority_factor_at`
(I3) · `idle_expiry` · `absolute_expiry` · `client_ip`.
**Invariants.** I1 It respects the concurrent-session limit (ADM-145). I2 It is revoked when its
account is disabled. I3 `authority_factor_at` is set when the session verifies an authority factor
(DM-37.I3), or when it authenticated the correlated AD account by Kerberos (DM-30.I6).
Correlation-derived grants count only while it is set. Every step-up of such a session verifies the
factor again. A failed verification clears the field, and so does a revocation of the factor.
**Lifecycle.** `active → expired | revoked`.

### DM-32 ApiToken · T · owner `platform/authn`
**Definition.** A credential that lets a script act as its owning account. **Replaces (ME):**
technician authtokens (ADM-141).
**Key attributes:** `owner_account_id` · `name` · `secret_hash` · `permission_subset` ·
`scope_narrowing` · `expires_at` (mandatory) · `last_used`.
**Invariants.** I1 Effective authority is the owner's current authority intersected with the
token's subset. A disabled owner makes the token dead. I2 The secret is shown once.
**Lifecycle.** `active → expired | revoked`.

### DM-33 Permission · R · declared by each module (EP-6)
**Definition.** A named capability that an operation or Action requires, such as
`objects.user.create`, `helpdesk.password.reset` or `secret.read:laps`. **Replaces (ME):**
task-level privileges (ADM-125).
**Key attributes:** `id` · `kind` (action, read, admin, secret) · `attribute_constrainable` ·
`risk` · `control_plane` (I3).
**Invariants.** I1 Every OpenAPI operation declares exactly one (`x-permission`). I2 Secret
values are reachable only through `secret.*` permissions (safe-primitives §3.7). I3 **Control
plane.** A permission is `control_plane` when it administers access itself: accounts, sessions or
API tokens of others, roles, role assignments, delegation scopes, connections and their credentials,
bindings, HybridLinks and attestations. **Backstop:** every permission whose `kind` is not `read`
and whose ID lies in the `authn`, `authz`, `delegation` or `connections` namespace must be
flagged. That covers `action`-kind permissions that start Operations, such as
`connections.takeover.attest` and `connections.hybrid_link.confirm`, and `secret`-kind ones such
as connection credentials. The check runs in EP-6 catalogue validation inside `Boot`, over the
whole catalogue, not in the Registrar. `platform/authn` and `platform/authz` are kernel packages
that never call the Registrar (ADR-0003 rule 4), so only the catalogue sees kernel- and
module-declared permissions alike. An unflagged permission fails start-up, so CI's
`compose/server` boot test catches it first. A permission outside those namespaces may also be
flagged. A `control_plane` permission is held only through an assignment to the account itself
(DM-36.I4), so it never crosses a correlation (DM-20.I7). It is never imported from ManageEngine
either (threat model TM-D21).
**Lifecycle.** `active → deprecated → removed` (X6).

### DM-34 Role · T · owner `platform/authz`
**Definition.** A named set of privileges. A privilege is a Permission plus a mode and
constraints. **Replaces (ME):** help-desk roles (ADM-125), built-in roles (ADM-126), requester
roles (ADM-117), technician templates (ADM-132), report restrictions (ADM-102) and the LAPS
role (ADM-060).
**Key attributes:** `name` · `built_in` · `privileges[]`: `permission`, `mode` (`execute` or
`request`), and constraints: attribute allowlist, template allowlist, report categories,
`max_batch` (1 means no bulk), `csv_allowed`.
**Invariants.** I1 Built-in roles ship as data and are read-only; clone one to change it.
`tenant-owner` holds every permission. I2 `request` mode means the Operation must pass the
workflow gate (DM-64).
**Lifecycle.** `active → archived`. A role can be archived only with no assignments, or through an
Operation that revokes them.

### DM-35 DelegationScope · T · owner `modules/delegation`
**Definition.** The set of directory objects a grant reaches. **Replaces (ME):** OU-based
(ADM-127), include/exclude group (ADM-129), cross-domain (ADM-130) and M365 (ADM-131) delegation,
and the "filter cloud users by AD OU" part of hybrid handling (ADM-169).
**Key attributes:** `entries[]`: connection, `root_kind`, `root_guid`, include or exclude,
`include_correlated` (AD entries only, default false), `entry_state` (`active`, `root_deleted`) ·
target filters (object kinds, `groups_include`, `groups_exclude`).

| `root_kind` | Provider | `root_guid` | Reaches | Evaluated against |
| --- | --- | --- | --- | --- |
| `naming_context` | AD | NC head GUID | every object in the domain NC | inventory ancestry |
| `ou_subtree` / `ou_one_level` | AD | OU GUID | the OU's subtree, or its direct children | inventory ancestry |
| `group_members` | AD or Entra | group GUID / object `id` | the group's transitive members (DM-17 edges) | inventory links |
| `entra_tenant` | Entra | tenant ID (DM-10 `directory_identity`) | every object of the Entra connection | the connection |
| `administrative_unit` | Entra | AU object `id` | the AU's direct members (users, groups, devices) | inventory AU-membership edges |

**Invariants.** I1 Roots are GUIDs. A moved root keeps its scope. A deleted root grants nothing and
never widens to the domain or the tenant (safe-primitives LF-31). A root restored from the Recycle
Bin (or from Entra deleted items) keeps its GUID, so its scope would silently return. Instead the
entry stays inactive until an audited Operation reactivates it. I2 AD entries are evaluated
against inventory ancestry and re-checked against the live parent chain at Plan (blueprint §11).
Entra has no ancestry and no NamingContext (DM-14). Its entries are evaluated against inventory
membership edges and re-checked live through Graph at Plan. AU membership is not transitive: a
group in an AU does not put its members in the AU
([administrative units](https://learn.microsoft.com/en-us/entra/identity/role-based-access-control/administrative-units)).
I3 Exclusion beats inclusion. I4 Counts and pages are computed after scope trimming (LF-39).
I5 `tier0` objects are outside every write scope in v1, in every root kind (ADR-0002 rule 9;
FD-11). For Entra, `tier0` covers holders of privileged directory roles and role-assignable groups
(definition: T-0007, Q1). Correlations carry `tier0` across directories in any state
(DM-20.I7). I6 **AD scope to Entra objects.** An AD entry with
`include_correlated` also reaches the Entra objects whose correlation (DM-20) with an AD object it
reaches is `matched`, but only for Entra-provider Actions such as licences (DM-20.I3). `matched` is
the only authorizing state (DM-20.I4: the Entra object is synced from that AD object and not
cloud-managed). A `candidate` or `broken` correlation grants nothing, so a cloud-only object
stamped with an AD anchor is never reached. It is re-evaluated at Plan from the live AD ancestry
and a live re-check of the correlation gate (DM-20.I5). An Entra object correlated to an AD `tier0`
object is itself `tier0` (DM-20.I7), so this never reaches it. It is off by default, so an OU
grant never reaches the cloud silently. Writes to
AD-mastered attributes of a synced object go to AD and need the AD scope anyway. I7 Objects in a
restricted-management AU (detected by `isManagementRestricted`) ignore tenant-wide application
permissions unless the application holds an Entra role scoped to that AU
([restricted management AUs](https://learn.microsoft.com/en-us/entra/identity/role-based-access-control/admin-units-restricted-management#programmability)).
Plan decides per Action. Property changes, delete, password reset and member or owner changes are
planned as `blocked` with a reason, never failing at apply. Licences, usage location and adding
the object to other groups remain allowed, which matters for I6.
**Lifecycle.** `active → archived` (only when unassigned).

### DM-36 RoleAssignment · T · owner `platform/authz`
**Definition.** It grants a subject a Role over a DelegationScope. **Replaces (ME):** the
technician↔role↔domain/OU mapping (ADM-125…130) and group-based delegation (ADM-128).
**Key attributes:** `subject` (account, directory group as connection+GUID, or automation policy) ·
`role_id` · `scope_id` (null for roles with no directory reach) · `valid_from` / `valid_until` ·
`granted_by` · `state`. `scope_id` (a DelegationScope, owned by `modules/delegation`) and an
automation-policy `subject` (owned by `modules/lifecycle`) are **opaque typed references**
`(kind, id)` from a platform table into module-owned rows. They are resolved through the EP-6
evaluator interface, with no foreign key across the layer (blueprint §2: core never imports
modules). A reference that no longer resolves grants nothing.
**Invariants.** I1 **No escalation.** The grantor must hold every privilege of the role over the
whole scope, or be `tenant-owner`. This is the class of CVE-2024-24409
([advisory](https://www.manageengine.com/products/ad-manager/admanager-kb/cve-2024-24409.html)).
The same test covers two indirect grants. Changing the membership of a group that is the subject of
an assignment needs every privilege that group grants (threat model TM-D18). A sign-in-relevant
change to a console-backing object needs every privilege the backed account holds (DM-30.I7).
I2 A group subject's membership is **directory** membership, resolved transitively from inventory
including primary-group edges. It is not token membership: it is broader than `tokenGroups`, which
leaves out other domains' domain-local groups
([tokenGroups](https://learn.microsoft.com/en-us/windows/win32/adschema/a-tokengroups)).
Deactivated links never count. Subject groups must be security groups (AD) or groups with
`securityEnabled = true` (Entra). That test also admits Microsoft 365 groups with
`securityEnabled = true` and mail-enabled security groups
([groups overview](https://learn.microsoft.com/en-us/graph/api/resources/groups-overview)). A
distribution group grants nothing. An Entra group with `visibility = Public` grants nothing either,
because anyone can join it without approval and so give themselves an activeDIQ role
([group](https://learn.microsoft.com/en-us/graph/api/resources/group)). The AD analogue
is TM-D18 (threat model §7.7). An AD group grants nothing, and health flags it, while its DACL lets
a broad principal change its membership: Everyone, Anonymous Logon, Authenticated Users, Domain
Users, Domain Computers or Users. The rights that count are Self-Membership, WP `member`,
GenericWrite, GenericAll, WRITE_DAC and WRITE_OWNER. A member grants only through its Account's
`directory_ref` (DM-30.I5), or through a correlation of that object, and only while the
correlation is `matched` (DM-20.I4), re-checked live at sign-in and at Plan (DM-20.I5). A
`candidate` correlation never carries a group grant across directories: an Entra admin who stamps
an AD anchor on a cloud-only user gains no AD-side authority through activeDIQ. An FSP member
grants only if its SID resolves to an object in a connected forest that is bound to an Account.
`sIDHistory` is not followed. Members lose rights when they leave the group or are disabled, within
sync freshness (ADM-128). `authz` resolves membership only through its port `authz.Membership`,
which `directory/inventory` implements (ADR-0003 F6, blueprint §7.5). **Correlation-derived
grants.** A group grant is correlation-derived when the group lives in the other directory from the account's sign-in identity. That means an AD
group for an `sso` account, which signs in through Entra, and an Entra group for a `directory`
account. Such a grant obeys two extra rules:
- It never carries `tenant-owner` or a `control_plane` permission (DM-20.I7). No group grant
  carries them, in either directory (I4).
- For an `sso` account, it counts only in a session that verified the authority factor (DM-30.I6).

I3 Effective authority is the union of assignments, and each privilege applies only
within its own assignment's scope. Role A's permission is never combined with scope B.
I4 **Control-plane authority is personal** (threat model TM-D17 rule 5). `tenant-owner` and every
`control_plane` permission (DM-33.I3) reach an account only through an assignment whose subject is
that account. activeDIQ refuses, when it is created, any assignment that gives a group subject (AD
or Entra) or an automation-policy subject a role holding either, so no such configuration ever
exists to sit dead. A role edit that would add a `control_plane` permission to a role held by such
a subject is refused the same way, and the role must be cloned instead. A permission that becomes
`control_plane` on upgrade (X6) could still leave one behind. The evaluator never grants it
through that subject, audits the drop, and health flags the assignment until it is narrowed or
revoked. Group delegation (ADM-128) is unaffected for every other role.
**Lifecycle.** `scheduled → active → expired | revoked`.

### DM-37 AuthenticatorEnrollment · T · owner `platform/authn` (EP-10)
**Definition.** A factor enrolled by an account (console MFA) or by an end user (FD-05 TOTP).
**Replaces (ME):** console 2FA enrollment (ADM-142). It is also the v1 slice of ADSSP enrollment.
**Key attributes:** `subject` (account, or directory user as connection+GUID) · `method` (totp,
webauthn, email_otp, sms_otp) · `sealed_secret` or `public_credential` · `authority_anchor`
(`ad_plane` or `owner_approval`, with the proof's audit reference; I3) · `label` · `last_used` ·
`state`.
**Invariants.** I1 Seeds are sealed and never returned after enrollment. I2 Zero-touch factors
(email or mobile already in AD or HR) are read live and are not enrollments. I3 **Authority
factor** (threat model TM-D19 rule 2). An `active` `webauthn` enrollment of an `sso` account with
an `authority_anchor` is an authority factor (DM-30.I6). The anchor is set at enrollment and never
changes. It is one of two kinds:
- `ad_plane`: the same ceremony proved the correlated AD account, through the connector's
  `VerifyUser` or SPNEGO (blueprint §11);
- `owner_approval`: a `tenant-owner` approved this enrollment beforehand, with step-up.

Every authority-factor enrollment is audited and notifies the account and every `tenant-owner`.
I4 Nothing on the Entra side can enrol, reset or remove an authority factor, and activeDIQ never
derives one from Entra authentication methods. A reset is a `tenant-owner` action with step-up,
and it is audited. The account itself may revoke its own factor only in a session that verified
that factor.
**Lifecycle.** `pending → active → revoked`.

### DM-38 CallerVerification · T · owner `modules/helpdesk` (ENH-09)
**Definition.** One challenge a technician issues to prove a caller is the target user before a

verification is ENH-09 (scope lock §3.5).
**Key attributes:** `technician_account_id` · `target` (connection+GUID) · `factor` ·

**Invariants.** I1 The destination comes only from data held before the call (AD or HR), never
from what the technician types. I2 The code is never stored in clear or logged. `code_mac` is a
keyed MAC under a key derived from the tenant data key (DM-02), never a plain hash, because a
plain hash of a six-digit code is enumerated in milliseconds. I3 A verified

recorded in the same audit event as the reset.
**Lifecycle.** `issued → verified | failed | expired | cancelled`.

## 4. Change: operations and jobs

### DM-40 Action · R · declared by modules (EP-3)
**Definition.** A typed write with `Plan`, `Apply`, `Verify` and `Inverse` (blueprint §4.2), for
example `objects.user.create` or `m365.licence.assign`. **Replaces (ME):** management tasks and
automatable tasks (ADM-107), orchestration blocks (ADM-045, ADM-109) and report actions
(ADM-098).
**Key attributes:** `id` · `permission` · `input_schema` · `reversibility` (reversible, lossy,
irreversible) · `providers` (ad, entra) · `capabilities`.
**Invariants.** I1 It is the only path to a directory write (X9). I2 `Plan` has no side effects.
I3 It declares `Inverse` or `Irreversible`. I4 No Action runs a free-form script. ME's custom
scripts (ADM-019, ADM-112) have no equivalent.
**Lifecycle.** `active → deprecated → removed` (X6). Templates, policies, workflows and report
definitions that reference it are migrated first.

### DM-41 Operation · T · owner `platform/operation` (guarantees: T-0047)
**Definition.** One intent to change directories, planned before it runs: a single edit, a
50,000-row CSV, a workflow request's execution, an automation run's step, act-on-results, or an
undo. **Replaces (ME):** bulk jobs, CSV imports and the execution side of workflow (ADM-010, 011,
034, 116).
**Key attributes:** `origin` (console, api, csv, workflow, automation, report_results, undo,
migration) · `initiator` chain (account, API token, automation policy, approvals) · `actions[]` ·
`input` (typed; secrets excluded) · `template_version` · plan summary (counts, reversibility,
approvals needed) · `plan_valid_until` · `undo_of` · `request_id` · `state`.
**Invariants.** I1 A plan always comes before apply. Authorization is checked at plan time and
re-checked per item at apply, against live ancestry. I2 Partial success is never reported as
success. I3 Undo is a new Operation, with `undo_of` set, through the same gate. I4 A plan older
than `plan_valid_until` must be re-planned before it is approved or applied.
**Lifecycle** (source: [ADR-0005](../decisions/0005-operation-pipeline-and-audit-trail.md) rule 3,
whose `transitions` block CI compares with the code).
`draft → planning → planned | no_change | plan_failed` (`no_change`: every item skipped, a success with no failure event); `planned → approved | awaiting_approval | rejected`
(gate); `awaiting_approval → approved | rejected`; `approved → queued → running →
succeeded | partially_succeeded | failed`; `running → cancelling → cancelled`. A re-plan returns
`planned`, `awaiting_approval` or `approved` to `planning`; approvals bound to an unchanged
`plan_hash` survive it. There is no `expired` state: an expired plan is re-planned and an abandoned
one is `cancelled`. Every pre-running state may go to `cancelled`.

### DM-42 OperationItem · T · owner `platform/operation`
**Definition.** One target, or one CSV row, of an Operation, with its ordered steps. Each step is
one Action applied to that target.
**Key attributes:** `item_no` · `target` (GUID, or "to be created" with a planned display DN) ·
`input_row` · `planned_diff` (attribute: before → after) · `steps[]` (`action_id`, `dc`,
`state`, `outcome`, `read_back`, `inverse_input`, `reversibility`) · `state`.
**Invariants.** I1 The idempotency key is `(operation, item, step)`; each claim carries an
`attempt` fence (ADR-0005 rule 6). I2 The before-state captured at plan is re-checked at apply,
inside `applying`. If it changed, the step fails `stale_state` and is never overwritten. I3 Verify reads back from the pinned DC that applied. If that DC stays unavailable past the verify window, it reads back from another DC, which the step records by name, or the step is `verify_failed` with reason `dc_unavailable` (ADR-0005 rule 5). I4 Inverse inputs contain no secrets,
and irreversible steps are flagged at plan.
**Lifecycle** (ADR-0005 rule 3). Item: `pending → planned | skipped | blocked`; `planned →
running → succeeded | failed | cancelled`; `planned → cancelled`; `succeeded | failed → undone` (an undo inverts the `verified` and `verify_failed` steps).
Step: `planned → applying → applied → verified | verify_failed`; `applying → failed` (denied,
stale_state, outcome_unknown, error, retries exhausted); `applying → not_run` (reconciler, operation
cancelling, no write happened); `planned → not_run`; `verified | verify_failed → undone`.

### DM-43 Job · execution record in River (global, registered) · owner `platform/jobs`
**Definition.** A unit of background execution that advances a domain record: an operation chunk,
a report run, a sync pass or a delivery. **Replaces (ME):** the scheduler's internal tasks.
**Key attributes:** `kind` (EP-5) · `args` (`tenant_id` + a typed reference to the domain record) ·
`unique_key` · `attempt` · `scheduled_at`.
**Invariants.** I1 A job is never the system of record. The OperationItem, ReportRun or
SyncCursor holds the truth, and a lost job is re-derived from it. I2 Args carry `tenant_id`, and
the wrapper establishes the tenant first: it runs the body in one `WithTenantTx`, or, for a
`ManagedTx` kind such as the operation kinds, hands it a tenant-bound transaction runner (ADR-0002
Jobs row as amended by ADR-0005 rule 6). Platform jobs are registered. I3 Only `platform/jobs`
imports River (ADR-0002 T5).
**Lifecycle.** River's states: `scheduled | pending | available → running → completed`, or
`running → retryable → … → discarded`, or `→ cancelled`
([JobState](https://pkg.go.dev/github.com/riverqueue/river/rivertype#JobState)).

### DM-44 Schedule · T · owner `platform/jobs`
**Definition.** A recurrence owned by one entity: an automation policy, a report schedule or a
cleanup policy. One shape serves all of them.
**Key attributes:** `recurrence` (hourly, daily, weekly, monthly, custom) · `time_zone` (IANA) ·
`window` · `next_run_at` · `owner_ref` · `state`.
**Invariants.** I1 The recurrence is evaluated in its time zone, and `next_run_at` is stored in
UTC. A local time skipped by DST runs at the next valid instant; a repeated one runs once.
I2 Misfires after downtime run once, never as a burst.
**Lifecycle.** `active ⇄ paused → deleted` (with its owner). **Replaces (ME):** scheduler options
(ADM-101, ADM-104).

## 5. Definitions

### DM-50 Template · T · owner `modules/objects`
**Definition.** A versioned recipe for creating or modifying one object kind: the form, defaults,
rules, naming, password, duplicate checks, allowed containers and follow-on steps. **Replaces
(ME):** creation templates (ADM-012), creation rules (ADM-013), template bulk-edit and copy
(ADM-014), modification templates (ADM-015, ADM-058), and group, computer, contact and OU
templates (ADM-049, 055, 061, 062).
**Key attributes:** `object_kind` · `provider` (ad, entra, hybrid) · `purpose` (create, modify) ·
`version` · form (sections; per field: editable, read-only, hidden, mandatory; default; pick list
DM-53) · `rules[]` (a condition AST that sets an attribute, adds a group or chooses a container) ·
`naming_formats` (DM-51) · `password_policy` (DM-52) · `duplicate_check` (attributes; scope:
domain, forest or Entra; ADM-020) · `allowed_containers` (OU GUIDs) · `post_steps[]` (Action ID +
parameters, e.g. licence assignment for ADM-027 or groups).
**Invariants.** I1 Published versions are immutable, and Operations pin one (X7). I2 Rules are
data; no scripts (DM-40.I4). I3 A template never grants authority. Every step is still checked
against the technician's privileges and scope. I4 Containers are GUIDs.
**Lifecycle.** `draft → published → archived`. Publishing creates version n+1. Copying a user
(ADM-016) is an input mode, not a stored entity.

### DM-51 NamingFormat · T · owner `modules/objects`
**Definition.** It derives a name from input attributes. **Replaces (ME):** naming formats and
conditional naming (ADM-017, ADM-018).
**Key attributes:** `purpose` (sAMAccountName, UPN prefix, CN, displayName, mail alias) ·
`alternatives[]` (condition + tokens: attribute part, case, literal, digits) · `collision_suffix`.
**Invariants.** I1 Output goes through the primitives: an RDN through P2; sAMAccountName length
and character rules are validated at plan. I2 The DC decides uniqueness (R9). I3 There are no
custom-script functions (ADM-019 has no equivalent).
**Lifecycle.** `draft → active → archived`. Template versions pin the version they use.

### DM-52 PasswordGenerationPolicy · T · owner `modules/helpdesk`
**Definition.** The rules for generated passwords. **Replaces (ME):** random password policy
(ADM-021), with ADM-022's options.
**Key attributes:** `length` · `classes` · `excluded_chars` · `first_char` · `dictionary` · `allowed_modes`.
**Invariants.** I1 A generated password is a `Secret` (X4). I2 The DC's effective policy (domain
or FGPP) is the final judge, and a rejection fails the item visibly. Whether ADM-022's "same as
logon name" and "blank" modes are offered is `[OPEN → user-lifecycle spec]` (§11 Q4).
**Lifecycle.** `active → archived`.

### DM-53 AttributeList · T · owner `modules/objects`
**Definition.** A managed pick list for an attribute, such as department, title or office.
**Replaces (ME):** organization attribute lists (ADM-037).
**Key attributes:** `attribute` · `connection_id` (optional) · `values[]`.
**Invariants.** I1 It constrains input only. Directory values outside the list are shown, never
rewritten.
**Lifecycle.** `active → archived`.

## 6. Automation and workflow

### DM-60 AutomationPolicy · T · owner `modules/lifecycle`
**Definition.** A versioned rule that selects objects and runs ordered Action steps on them, with
delays, on a trigger. **Replaces (ME):**
- scheduled automation (ADM-104), automation policies (ADM-105), controlled automation (ADM-106);
- the disable and delete policies (ADM-043, ADM-044) and the cleanup policy (ADM-147);
- HR, CSV and database provisioning (ADM-039, 040, 041), movers (ADM-042);
- expiry reminders (ADM-047), the offboarding blocks (ADM-045).

**Key attributes:** `owner_account_id` · `trigger` (`schedule` DM-44; `directory_state`, for
example "user became disabled", observed by sync whoever made the change; `operation_event`, an
activeDIQ Action that succeeded; `data_source` DM-63) · `selector` (report definition +
parameters, data-source rows, or the triggering object) · `steps[]` (Action ID, parameters, delay
after the previous step) · options (`controlled`, `skip_changed_by_last_run`, `max_objects`) ·
`execution_owner` (`activediq`, or `external` during migration, MIG-14) · `version` · `state`.
**Invariants.** I1 Every run produces Operations (X9). Automation is never a side door. I2 It acts
as itself: the policy is a RoleAssignment subject (DM-36), so its reach is explicit, and DM-36.I1
stops it from exceeding its grantor's reach. I3 If a run plans more than `max_objects` items, it
holds for approval instead of applying (blast-radius guard). The approval is a Request on the
workflow whose definition matches the hold, or else the kernel's single approval by an account
holding `operation.approve` over every item's scope that is neither the policy owner nor in the
initiator chain (ADR-0005 rule 8). I4 While in `shadow`, it plans and
compares but never applies.
**Lifecycle.** `draft → shadow → active ⇄ paused → archived` (`shadow` is optional). It is flagged
`orphaned` when its owner is no longer active. It keeps running, and tenant owners are notified.

### DM-61 PolicyProgress · T · owner `modules/lifecycle`
**Definition.** One object's position in a multi-step policy, such as disable → move after 30
days → delete after 90.
**Key attributes:** `policy_id` · `object_guid` · `step` · `entered_at` · `next_due_at` ·
`last_operation_id` · `state`.
**Invariants.** I1 One row per (policy, object). I2 A due step runs only if the object still
matches the selector when it is planned, so a re-enabled user leaves the track and is never
deleted.
**Lifecycle.** `active → completed | exited | failed`.

### DM-62 AutomationRun · T · owner `modules/lifecycle`
**Definition.** One firing of a policy's trigger. **Replaces (ME):** automation execution history
(ADM-114).
**Key attributes:** `policy_id` + `version` · `fired_at` · `selected_count` · `operation_ids[]` · `state`.
**Invariants.** I1 One run per (policy, firing). The key makes a retried firing a no-op. I2 Any
failure notifies the owner (ADM-114).
**Lifecycle.** `started → completed | completed_with_errors | failed | held | skipped`.

### DM-63 DataSource · T · owner `modules/lifecycle`
**Definition.** An external feed of identity data: an HR system, a CSV feed or a database.
**Replaces (ME):** HCM integrations, CSV locations and database sources (ADM-039, 040, 041).
**Key attributes:** `kind` (hr, csv, database) · endpoint settings · `sealed_credentials` ·
`field_mapping` · `match_rule` (source key ↔ directory attribute, e.g. `employeeID`) ·
`row_hashes` (change detection) · `state`.
**Invariants.** I1 It is configured only through the API. A CSV "drop" is an upload or a
blob-store prefix, never a path on the server host (ADR-0002 Configuration row). I2 Rows match
directory objects only by a stable key, never by name. I3 Its credentials are not directory
credentials. They are unsealed by `platform/keys` for the integration runner only.
**Lifecycle.** `draft → active ⇄ paused → archived`.

### DM-64 WorkflowDefinition · T · owner `modules/workflow` (EP-4)
**Definition.** The approval process for a class of requests. **Replaces (ME):** business
workflows (ADM-116), workflow agents (ADM-117), assigning rules (ADM-118), SLAs (ADM-119) and
managers as approvers (ADM-121).
**Key attributes:** `version` · `applies_to` (Action IDs, templates, scopes, requester roles) ·
`stages[]` (review, approval or execution; assignees: accounts, roles, or dynamic "manager of
target" / "manager of requester" with a fallback; quorum any or all) · `assigning_rules[]` ·
`sla_levels[]` (up to 3: after T, reassign, re-prioritise, notify or close) · `auto_execute`.
**Invariants.** I1 Separation of duties: a requester never reviews or approves their own request.
I2 Dynamic assignees are resolved at submission and recorded on the Request. I3 Requests pin the
version.
**Lifecycle.** `draft → published → archived`.

### DM-65 Request · T · owner `modules/workflow`
**Definition.** One requested change moving through a workflow. It wraps exactly one planned
Operation. **Replaces (ME):** workflow requests and the Requests tab (ADM-116, ADM-120).
**Key attributes:** `definition_version` · `requester` · `operation_id` (1:1) · `plan_hash` ·
`priority` · `stage` · `due_at` · `external_ticket` (ITSM, DM-85) · `state`.
**Invariants.** I1 Approvals bind to `plan_hash`. If a re-plan changes the diff, they reset.
I2 Resending failed items (ADM-120) creates a new linked Operation.
**Lifecycle.** `draft → submitted → in_review → in_approval → approved → executing → closed`
(completed, partial or failed). It can also end `rejected`, `cancelled` or `expired` (SLA).

### DM-66 ApprovalDecision · T · append-only · owner `modules/workflow`
**Definition.** One reviewer's or approver's decision on one stage.
**Key attributes:** `request_id` · `stage` · `decider` · `decision` (approve, reject, reassign) ·
`plan_hash` · `comment` · `at`.
**Invariants.** I1 Immutable (X5). I2 It counts toward quorum only if the decider was an assignee
at that time and is not the requester. I3 Its `comment` is free text about people, so it is
erasable under X11.
**Lifecycle.** `recorded` (terminal, and derived: the row exists).

### DM-72 ReportRun · T · owner `modules/reports`

**Key attributes:** `definition_version` · `parameters` · `runner` · `scope_applied` · `as_of`

### DM-73 ReportSchedule · T · owner `modules/reports`
**Definition.** A recurring run plus delivery. **Replaces (ME):** scheduled reports (ADM-101) and,

**Key attributes:** `definition_id` · `parameters` · `schedule` (DM-44) · `owner_account_id` ·
`delivery` (accounts or external addresses, formats, attachment or link, notify only if data) ·
`execution_owner` (MIG-14) · `state`.
**Invariants.** I1 Each run uses the owner's authority at that moment. If the owner is disabled,
the schedule pauses. I2 Delivery to an external address requires its own permission.
**Lifecycle.** `active ⇄ paused → archived` (plus `shadow` while ME still runs it).

## 8. Evidence and integration

### DM-80 AuditEvent · T · append-only · owner `platform/audit` (guarantees: T-0047)
**Definition.** One entry in activeDIQ's own audit trail. Each tenant has one hash chain.
**Replaces (ME):** the help-desk audit (ADM-137), admin audit (ADM-138), technician logons
(ADM-139) and automation audit history (ADM-114).
**Key attributes:** `seq` (per tenant, gapless) · `at` · `kind` (registry, EP-7) · `actor` chain
(principal, plus the API token, automation policy and approvals it acted through) · `targets`
(connection+GUID with a display snapshot) · `operation`/`item`/`request` refs · `outcome` ·
`details` (typed per kind) · `verification_factor` (ENH-09) · `client_ip` · `prev_hash` · `hash`.
**Invariants.** I1 One chain per tenant. Events are chained at commit under the tenant's
`audit_head` row lock, so `seq` is commit order and has no gaps (ADR-0005 rule 11). Personal
values are `PersonalRef`s, never clear text (rule 12).
I2 Immutable (X5). Retention deletes only below a checkpoint (DM-81). I3 Every operation step,
sign-in, RBAC change, settings change, secret read, presence grant, enrollment and credential
change emits an event. I4 Details never carry a `Secret`. Targets keep a display snapshot of the
DN and name as they were at the time, because DNs change. That snapshot is personal data and is
erasable under X11, subject to §11 Q9.
**Lifecycle.** `appended → checkpointed → archived → purged`, all derived (X5), never a column.
`checkpointed` means `seq` ≤ the `seq` of the tenant's latest ChainCheckpoint (DM-81).
`archived` means the event's partition has been exported, and it stays verifiable from the export
and the checkpoints. `purged` means the retention role dropped the partition, which it may do
only below a checkpoint (I2).

### DM-81 ChainCheckpoint · T · append-only · owner `platform/audit`
**Definition.** A signed statement of the chain head at a given `seq`.
**Key attributes:** `seq` · `hash` · `signed_at` · `signature` · `key_id`.
**Invariants.** I1 Checkpoints are kept for the tenant's life, so verification starts from any
retained checkpoint after events are purged. I2 Signed by the tenant's Ed25519 checkpoint key
valid at that `seq` (chained key windows), sent to every SIEM sink and included in every export
(ADR-0005 rule 11).
**Lifecycle.** `recorded` (terminal, and derived: the row exists).

### DM-82 NotificationChannel · T · owner `platform/notify` (EP-9)
**Definition.** A configured way out: SMTP or a mail API, an SMS gateway, or a SIEM (syslog, CEF,
HTTP). **Replaces (ME):** mail, SMS and proxy settings (ADM-205) and SIEM forwarding (ADM-198).
**Key attributes:** `kind` · `settings` · `sealed_credentials` · `last_test` · `state`.
**Invariants.** I1 Credentials are sealed and never returned. The egress proxy is a platform
setting.
**Lifecycle.** `draft → active ⇄ disabled → archived`.

### DM-83 NotificationTemplate · T (shipped defaults + overrides) · owner `platform/notify`
**Definition.** The message for a purpose and channel kind. **Replaces (ME):** notification
templates and profiles (ADM-204).
**Key attributes:** `purpose` · `channel_kind` · `locale` · `subject` · `body` with typed
placeholders.
**Invariants.** I1 Placeholders come from the purpose's typed variable set and are rendered
through the output encoders. No placeholder resolves to a `Secret` (§11 Q4).
**Lifecycle.** `active → archived`.

### DM-84 Delivery · T · owner `platform/notify`
**Definition.** One attempt to deliver one message to one recipient. **Replaces (ME):**
notification history (ADM-204).
**Key attributes:** `channel_id` · `template_version` · `recipient` · `source_ref` (operation,
report run, request, reminder) · `attempts` · `provider_message_id` · `state`.
**Invariants.** I1 It stores metadata and variable references, not rendered bodies.
**Lifecycle.** `queued → sent`, or `queued → failed → (retry) → sent | given_up`.

### DM-85 ItsmConnection · T · owner `modules/itsm`
**Definition.** A link to a service-desk system. One adapter shape covers every system.
**Replaces (ME):** the ServiceNow and ServiceDesk Plus integrations (ADM-191, ADM-192).
**Key attributes:** `kind` (servicenow, servicedesk_plus) · `endpoint` · `sealed_credentials` ·
`field_mapping` · `modes` (inbound requests, status write-back) · `state`.
**Invariants.** I1 An inbound ticket creates a Request (DM-65), never a direct write.
**Lifecycle.** `draft → active ⇄ disabled → archived`.

**Customer-visible prerequisite: hybrid AD↔Entra authority.** This is the same in every profile.
Three capabilities cross from one directory to the other:
- an AD scope reaching the correlated Entra objects (`include_correlated`, DM-35.I6);
- AD group grants for SSO technicians (DM-30.I5, DM-36.I2);
- routing a synced object's AD-mastered attributes to AD (DM-20.I3).

Each needs `matched` correlations (DM-20.I4), so each Entra tenant must have:
1. `blockCloudObjectTakeoverThroughHardMatchEnabled` and `blockSoftMatchEnabled` both on;
2. a current Global Administrator attestation of those two flags (DM-10.I7), renewed at least
   every 90 days or after a sync-feature change;
3. a confirmed HybridLink for each domain (DM-21.I2).

Two more customer-visible consequences follow from the threat model (TM-D17, TM-D19):
- A correlation that forms while an attestation has lapsed, or whose Entra object our sync once
  saw cloud-only or cloud-managed, needs a `tenant-owner` re-confirmation before it is `matched`
  (DM-20.I4(g)). Correlations that already exist at the first attestation do not.
- A hybrid SSO technician enrols one activeDIQ passkey, once, proving their AD password or with a
  `tenant-owner`'s approval. They use it once per session before AD group grants apply (DM-30.I6,
  DM-37.I3). The threat model §6.9 assigns this notice to factory-director, like D-0009.
- `tenant-owner`, and roles that administer RBAC, delegation scopes or connections, are assigned
  to named accounts only, never to an AD or Entra group (DM-36.I4, TM-D17 rule 5). A customer who
  delegates administration through a group in ManageEngine (ADM-128) keeps group delegation for
  every other role. Migration never imports those administrative grants (TM-D21); a `tenant-owner`
  assigns them to named accounts.

Without these, every correlation stays `candidate`. Entra objects are still fully manageable,
but only through Entra-root scopes (`entra_tenant`, `administrative_unit`, Entra
`group_members`; DM-35). AD objects are managed through AD scopes as usual. SSO technicians keep
their Entra group grants and grants made to the account itself, but get no AD group grants. The
same degraded mode applies to a session without the authority factor. The
connection health page and the setup guide state this; docs and onboarding must not promise
hybrid reach without it.
