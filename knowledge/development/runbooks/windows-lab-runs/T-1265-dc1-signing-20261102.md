# T-1265 — dc1 (VM 119, 192.168.1.250) LDAP signing: restore and root cause

Run 2026-11-02 ~08:00–08:40Z from the build host, every dc1 step under `with-dc1-lock` (A-0025, lab only). No secrets printed.
dc1 moved from .9 to .250 in A-0032; `WIN_LAB_DC_ADDR=192.168.1.250`.

## Before (dc1-policy check)

```
LDAPServerIntegrity = 1
LdapEnforceChannelBindingTokens = 2
cleartext simple bind to 192.168.1.250:389 with a dummy password -> resultCode 49 (invalidCredentials)
```

## Root cause

**The Default Domain Controllers Policy still defines `LDAPServerIntegrity` as 1, and Group Policy rewrites the registry value from it.**
`C:\Windows\SYSVOL\domain\Policies\{6AC1786C-016F-11D2-945F-00C04fB984F9}\MACHINE\Microsoft\Windows NT\SecEdit\GptTmpl.inf`
(unchanged since 2026-10-27 12:15Z, the original promotion) contained
`MACHINE\System\CurrentControlSet\Services\NTDS\Parameters\LDAPServerIntegrity=4,1`. `secedit /export` on dc1 shows the same line, and
`gpresult` lists Default Domain Controllers Policy as applied. The Security Settings engine re-applies that template on every
boot and refresh, so any registry write of 2 (T-0566 on 2026-10-30, `gssapi-ready.ps1`) lasts only until the next policy run.
dc1 booted un-cleanly on 2026-10-30 17:38Z (event 41/6008) and was restarted on 2026-11-01 15:14Z and 15:19Z; Directory Service
event 2889 (clear-text/unsigned binds accepted) was logged on 2026-11-01 15:35Z, i.e. signing was not required by then.

Ruled out:
- **Repo scripts.** grep over `main` and every `factory/*` branch: `gssapi-ready.ps1` is the only writer of either value and only ever writes 2; `gssapi-lab run` never touched them; nothing restores a captured "before" value.
- **Snapshot rollback.** Proxmox task history for the window shows only starts (qmstart 2026-10-30 05:07Z, 2026-11-01 13:25Z, 2026-11-02 05:38Z) and console sessions (note by the CEO, 2026-11-02); no rollback.
- **Scheduled task** touching the value: none on dc1.

Not determinable: the exact second of the reset (the NTDS\Parameters key last-write time reads 2026-11-02T21:21Z, and dc1's clock jumps
by about a day relative to the host, so it is not usable as evidence). The boots on 10-30 17:38Z and 11-01 15:14Z/15:19Z are the
candidates; the mechanism is the same for each.

## Fix

`dc1-policy restore` (lab/windows/bin/dc1-policy) now fixes the cause as well as the symptom, in this order:
1. sets the template line to `…LDAPServerIntegrity=4,2`, bumps the GPO version in `GPT.INI` and in the AD object, `gpupdate /target:computer /force`;
2. writes the two registry values to 2 (`LdapEnforceChannelBindingTokens` was already 2);
3. reboots dc1 (channel binding is read at boot), waits for NTDS, then runs `check`.

```
before:
  LDAPServerIntegrity = 1
  LdapEnforceChannelBindingTokens = 2
  GPO GptTmpl.inf LDAPServerIntegrity = 1
set LDAPServerIntegrity=4,2 in the Default Domain Controllers Policy ..., bumped its version, gpupdate
wrote LDAPServerIntegrity=2 and LdapEnforceChannelBindingTokens=2; rebooting dc1
after (post-reboot):
  LDAPServerIntegrity = 2
  LdapEnforceChannelBindingTokens = 2
  Default Domain Controllers Policy GptTmpl.inf LDAPServerIntegrity = 2
```

## After (dc1-policy check, a later session, post-reboot)

```
LDAPServerIntegrity = 2
LdapEnforceChannelBindingTokens = 2
Default Domain Controllers Policy GptTmpl.inf LDAPServerIntegrity = 2
cleartext simple bind to 192.168.1.250:389 as svc-activediq@win.activediq.test -> resultCode 8 (strongerAuthRequired)
dc1-policy: enforced
```

## Correction to the ticket's test: a dummy-password bind cannot prove enforcement

The ticket (and the first version of the probe) used a cleartext simple bind with a **dummy** password and expected 8. Measured on
dc1 at 2/2 + GPO 2 right after the restore: a dummy-credential bind answers **49**, a bind with the valid `svc-activediq` credentials
answers **8** (the DC checks the credentials before it reports "server requires binds to turn on integrity checking"; this matches
the 2026-10-28 T-0210 proof, which bound with valid credentials and got 8 / `DSID-0C090343`). So the 49 seen on 2026-11-01
was not proof by itself; the registry value 1 was. `bind_probe` now takes the lab service account (password from `WIN_LAB_SVC_PASSWORD`,
never printed) and `check` fails if that password is missing instead of passing on a bind that cannot tell.
