## 1. Acceptance 1 — the four msDS-Repl* attributes

Base search, scope base, for all four attributes plus a sentinel (`currentTime` on the rootDSE, `distinguishedName` elsewhere) at five bases.
Cell = entry returned, attributes of the four returned.

| Principal | State | rootDSE | domain head | config head | schema head | NTDS Settings |
| --- | --- | --- | --- | --- | --- | --- |
| administrator | no grants | entry, 0/4 | entry, 0/4 | entry, 0/4 | entry, 0/4 | entry, 0/4 |
| svc-activediq | no grants / S1 | entry, 0/4 | entry, 0/4 | entry, 0/4 | entry, 0/4 | entry, 0/4 |

What is established:

- **A read with no right succeeds and returns an attribute-less entry, never an error** (`t1510-none`, `svc-activediq`: LDAP success, entry present, sentinel present, none of the four). This is the T-0404 shape and the premise of TM-D31 rule 4 / TM-F-RIGHTS (c)(d). Also true for the right-holder and for Administrator.
- `;binary` variants and the `+` request were also tried as Administrator in a probe (not in the driver): nothing returned either.
- Documented location: rootDSE ([MS-ADTS 3.1.1.3.2.28](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-adts/b4a0b2bf-95f9-40b4-9301-834ccadea40c)). **This lab did not confirm it.**

## 2. Acceptance 1 — what was NOT established

**Where the attributes live and whether Monitor-Topology alone is enough are not determined.** The Administrator control, which must return data if the data exists,
returned none at any of the five bases, because dc1 has no inbound replication partner, no pending operation and no KCC failure
(`repadmin /showrepl`, `/queue`, `/failcache` all empty). On this DC an empty answer cannot be told from a denied one, so the table in §1 proves
nothing about the right in either direction. `repl-rights-lab` prints `INCONCLUSIVE` for this reason and the judge (`lib/replrights.py`) refuses to
call the right "sufficient" or "insufficient" unless the Administrator control returned values (offline tests pin that).

Consequence for the build (T-1512), unchanged from TM-D31: location and right stay `[UNVERIFIED — LAB: Windows]`; rule 4 holds (an empty read is "Not reported",
never "Healthy"); rule 3 is **not** triggered (nothing shows a wider right is needed) and also not discharged.

## 3. Writes attempted beyond the read, disclosed

While trying to get a non-empty control I ran one `repadmin /add` of the Configuration NC from a non-existent source name on dc1. It answered "Successfully enqueued"
and left nothing behind (`/queue` 0 items, `/failcache` none, `/showrepl` no partner, checked straight after). I then attempted to create a fake `server`/`nTDSDSA`/`nTDSConnection`
in the Configuration NC so the KCC would record a failing partner; **the permission layer denied it and it was not run**. That is a change to dc1's replication topology
outside "read four attributes", so it needs an explicit go-ahead; I did not retry or route around the denial.

## 4. Rule 7 — DirSync under LDAP_DIRSYNC_OBJECT_SECURITY | INCREMENTAL_VALUES, from the domain head

Per principal: baseline pass, a live user modified (`description`), a second user deleted (Recycle Bin on, so a logically deleted object), then a delta pass with the cookie.

| Principal | live change seen | delete seen | isDeleted | whenChanged | originating time | msDS-ReplAttributeMetaData |
| --- | --- | --- | --- | --- | --- | --- |
| administrator | yes | **yes** | TRUE | not returned | none | not returned |
| svc-activediq (default account) | yes | **yes** | TRUE | not returned | none | not returned |
| t1510-mon | yes | **yes** | TRUE | not returned | none | not returned |
| t1510-none | yes | **yes** | TRUE | not returned | none | not returned |

- **A delete is delivered to the default account and to a no-right account**, as an entry with `objectGUID` and `isDeleted=TRUE`, with no Get-Changes, no right on `CN=Deleted Objects`.
  Object security does filter the live view: Administrator's baseline held 13055 entries against 12947 for the others.
- **No originating time arrives.** The delete entry carried neither `whenChanged` nor `msDS-ReplAttributeMetaData` (requested; not returned). So rule 7's "Basis: DC time, originating" cannot be taken from this feed; the build keeps Basis "observed" (reports-2a, TM-D31 rule 6/7).
- Caveat on method: a freshly created object did not appear in anyone's feed as a live add (not even Administrator's) within 5 one-second polls (`precheck victim_visible_before_delete=0`);
  the DirSync snapshot lagged recent creations until the object changed. The delete itself was still delivered to every principal for an object its feed had never shown. A consumer must therefore treat a tombstone entry for an unknown GUID as "removed, never observed", not as an error.
- For security-architect (R2): any authenticated account that can run DirSync with OBJECT_SECURITY learns the GUIDs of deleted objects. That is existence only (no attributes), and the account never needed Get-Changes.
