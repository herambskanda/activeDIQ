## What the first run found

1. `gssapi-ready.ps1` had two defects: `ConvertTo-Secure` is not a cmdlet, and under `common.ps1`'s StrictMode a missing registry value threw. Both fixed. The
   gMSA also needs `Administrator` among the principals allowed to read `msDS-ManagedPassword` (WinRM runs as Administrator, not as the computer account).
   `ktpass` flags (`/crypto AES256-SHA1 /ptype KRB5_NT_PRINCIPAL +setupn`) worked as written: a 91-byte keytab, one AES256 entry, kvno 3.
2. dc1's clock is 12h30m ahead of real time, so the KDC answered every AS-REQ with KRB_AP_ERR_SKEW (bug **T-0850**).
3. With the clocks aligned, `ad.Open` still cannot log in to the WS2025 KDC: go-krb5 sends PA-REQ-ENC-PA-REP, the KDC sets EncPARep without PA-FX-FAST in the
   encrypted pa-data, and the library rejects the AS-REP ("KDC did not respond appropriately to FAST negotiation"). Bug **T-0846** (product, P1). The
   tests that drive the same handshake with `client.DisablePAFXFAST(true)` pass, and the two `…Open…` tests stay red until T-0846 is fixed.
4. The gMSA string-to-key assumption (UTF-16 password re-encoded as UTF-8, host-style salt, kvno from `msDS-KeyVersionNumber`) is **confirmed**: the derived keytab binds.
5. `LdapEnforceChannelBindingTokens` is read at boot: setting it to 0 at runtime left the wrong-binding test passing (still enforced), so the enforcement
   cannot be flipped without a reboot. Not done a second time (shared DC); the broken-run proof below is by mutation plus the DC's own event.
