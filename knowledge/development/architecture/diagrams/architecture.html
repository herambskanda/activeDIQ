How activeDIQ is put together

A server that manages Active Directory and Entra ID through one narrow gate, the connector. Everything below is read from knowledge/development/architecture/blueprint.md and the ratified ADRs. Where they disagree, the ADR wins.

The public API is the product boundaryEvery click and every script is an OpenAPI operation. The web console is one client and has no private endpoints.
The connector is the only path to a directoryDirectory credentials exist only inside it, and it reaches a directory only through typed operations.
Modules plug into the kernel, never the reverseThe platform kernel imports nothing above it, so it can be extracted and shared with UEM later.
Modules are islandsA server module never imports another. They cooperate through kernel registries, by ID. A leaver policy composes objects.user.disable and m365.licence.remove without importing either.
Credentials hold by constructionOutside the connector, only compose/server, compose/connector and the future compose/t0connector may import it. The agent and connector never link a package that reaches the database.
Only generated lists name a modulemodules.gen.go for server and agent, modules.gen.ts for the web. Adding a module is adding a directory, not editing core.
Kernel asks through portsWhen the kernel needs directory-owned data, it declares a port and a directory package implements it. The kernel never imports the directory.

Example: a bulk modify (ADM-034). Every write in the product takes this path. The order is the point: plan and authorise first, show a preview, then write each step with a live re-check, and audit in the same commit as the outcome.

  1. API receives the requestCarries an Idempotency-Key, so a retry never repeats the work.
    apihost
  2. PlanThe Action's Plan reads live state on the pinned domain controller, computes the diff and marks each step reversible, lossy or irreversible.
    operationclient
  3. Authorise every itemChecked over live facts, not cached ones, so delegation is evaluated against what is true now.
    authz
  4. Preview to the adminThe UI shows what will change, with lossy and irreversible steps called out. Approvals bind to a hash of the plan.
    web consolegate
  5. Enqueue chunk jobsWork is split into chunks and queued on the Postgres-backed job queue.
    jobs
  6. Per step: claim, then writeThe claim is committed before the write. The write checks a digest and re-reads live state, then goes through the connector as a pinned, conditional write.
    client.Writeconnector
  7. Record outcome and audit togetherThe outcome and its audit event land in one database commit, so neither can exist without the other.
    auditPostgreSQL
  8. Verify, then notifyA read-back on the pinned controller confirms the change. The change also reaches the inventory through the change feed, linked to the operation ID.
    notifyinventory

Other flows in blueprint §14: inventory sync, help-desk reset with one-time code, scheduled report, remote connector enrolment, and signed updates with automatic rollback.

One codebase, three compositions, chosen at build time from a manifest. Adapters may differ between profiles. Capabilities may not: where something needs Windows, it runs on a customer Windows host that both profiles can reach.

windows MSI · v1

  • Windows service running cmd/server with the server and embedded connector roles
  • Providers: AD and Entra
  • Kerberos through SSPI with a gMSA
  • Keys sealed with DPAPI-NG or TPM
  • PostgreSQL 18 bundled, or the customer's PG 16+

linux-oci images · v1

  • Container running cmd/server with the server and embedded connector roles
  • Providers: AD and Entra
  • Kerberos through krb5 with an AES keytab
  • Keys from TPM2, KMS, Vault or a passphrase
  • Customer PG 16+, or the upstream PG 18 image pinned by digest

saas CI only, not shipped

  • Our cell per region: stateless cmd/server replicas, managed PostgreSQL, our own edge
  • Entra only in the cell
  • AD reached through a connector at the customer site, dialling out over mTLS, so AD credentials never leave the customer
  • Keys in KMS

Optional on either self-hosted profile: a remote cmd/connector for another forest, DMZ or branch; cmd/edge for end-user access (M4); cmd/agent on domain controllers and file servers (M3). Self-hosted installs have exactly one tenant, created at install, and run the same row-level-security code path as SaaS.
